# 1.1 What is a Distributed System?

Let's start with the most fundamental question:

> **What makes a system distributed?**

A distributed system is a system in which **multiple independent computers work together to provide a single service or system to users**.

The important word is **independent**. Each computer has its own CPU, memory, operating system, network connection, and can fail independently of the others.

For example, imagine a web application running on one server:

```text
User
  ↓
Server
  ↓
Database
```

If the application server is one physical/virtual machine, this is not necessarily a distributed application simply because it talks to a database. The definition depends on what we're considering as the system and which independent machines participate in it.

Now imagine:

```text
                 ┌── API Server 1 ──┐
User ── Network ─┼── API Server 2 ──┼── Database
                 └── API Server 3 ──┘
```

There are now multiple application servers cooperating to provide the same application.

If Server 2 crashes, Servers 1 and 3 can potentially continue serving users.

That's a distributed system.

---

## Single-machine vs distributed systems

Consider a small application running entirely on one machine:

```text
                    Machine
        ┌──────────────────────────┐
User →  │ Application + Database   │
        └──────────────────────────┘
```

There is something very attractive about this architecture: **it is simple**.

You have one machine, one operating system, one application process, and perhaps one database process. Communication between components can be extremely fast because much of it happens locally.

But that machine has limited resources.

Suppose your application receives more and more traffic. Eventually its CPU, memory, disk, or network capacity may become insufficient.

You could buy a bigger machine:

```text
              Bigger machine
        ┌──────────────────────────┐
User →  │ Application + Database   │
        └──────────────────────────┘
```

This is **vertical scaling**: making one machine more powerful.

Eventually, however, there are practical limits. You can't indefinitely keep buying a larger machine.

Another approach is to use multiple machines:

```text
                    ┌── Server 1 ──┐
                    │              │
User → Load Balancer ┼── Server 2 ──┼── Database
                    │              │
                    └── Server 3 ──┘
```

Now work can be distributed across several machines.

This gives us the fundamental motivation behind distributed systems:

> **Instead of trying to make one machine do everything, we can make multiple machines cooperate.**

But that introduces an enormous amount of complexity, because those machines must communicate over a network—and networks fail.

---

# Why do we distribute systems?

There isn't one single reason.

The major reasons are **capacity, availability, performance, and geographical distribution**.

### 1. More capacity

Suppose one API server can process 1,000 requests per second.

If you have three independent API servers, you can potentially process roughly 3,000 requests per second, assuming the rest of the system can handle the additional load.

This is the basic idea behind **horizontal scaling**.

Instead of:

> "Make this machine bigger."

we say:

> "Add more machines."

---

### 2. Availability

Suppose you have only one API server.

If it crashes:

```text
User → API Server ❌
```

Your service is unavailable.

With multiple servers:

```text
                 ┌── Server 1 ❌
User → LB ───────┼── Server 2 ✓
                 └── Server 3 ✓
```

the system can potentially continue serving requests.

This leads to our first important distinction.

## Availability

**Availability describes whether the system is operational and able to serve requests when users need it.**

A highly available system is designed to minimize periods during which users cannot use the service.

For example, if an API is unavailable for five minutes because its only server crashed, it has experienced an availability problem.

Availability is therefore largely concerned with:

> **"Can I use the system right now?"**

---

# Reliability

Reliability is related to availability, but they are not the same thing.

**Reliability is about the system continuing to behave correctly and consistently over time.**

Imagine an API that is technically available but occasionally processes a payment twice.

The server responds successfully:

```text
HTTP 200 OK
```

but the system has done the wrong thing.

That is a **reliability problem**, even though the service was available.

Another example is a file-processing system that occasionally loses uploaded jobs.

Users can access the system, but the system doesn't reliably complete the work it promises to perform.

So:

**Availability:**  
> Is the system up and usable?

**Reliability:**  
> Does the system continue doing what it is supposed to do correctly?

They overlap, but they measure different properties.

---

# Performance

**Performance describes how quickly and efficiently the system performs its work.**

For a web API, common performance measurements include:

- response latency
- throughput
- CPU usage
- memory usage
- database query time

Suppose two APIs are both available:

```text
API A → response in 50 ms
API B → response in 5 seconds
```

Both are available, but their performance is very different.

This gives us another important distinction:

> **Availability asks whether the system responds. Performance asks how well and how quickly it responds.**

A system can therefore be:

- highly available but slow
- fast but frequently unavailable
- both fast and highly available
- neither

---

# Scalability

Now we can introduce **scalability**.

Scalability describes a system's ability to **handle increasing workload by adding resources**.

Suppose your application currently handles:

> 1,000 requests/second

and traffic grows to:

> 10,000 requests/second.

A scalable architecture should allow you to increase capacity rather than simply collapsing under the additional load.

For example:

```text
1000 RPS

       ┌── Server 1
LB ────┤
       └── Server 2


10000 RPS

       ┌── Server 1
       ├── Server 2
LB ────┼── Server 3
       ├── Server 4
       ├── Server 5
       └── Server 6
```

This is horizontal scaling.

But notice something important:

> **Scalability is not the same as availability.**

Adding six servers may increase your capacity. It can also improve availability because you now have redundancy.

But those are **two different benefits**.

The reason six servers can process more requests is scalability.

The reason the system can potentially survive one server failing is availability/fault tolerance.

---

# Fault tolerance

Now we get to another term that is particularly important in distributed systems.

**Fault tolerance is the ability of a system to continue operating when some component fails.**

Suppose we have:

```text
        ┌── Server 1 ✓
User → LB ├── Server 2 ❌
        └── Server 3 ✓
```

If the system continues serving users despite Server 2 failing, the architecture has some degree of **fault tolerance**.

The key idea is:

> **A fault-tolerant system expects failures and is designed to continue operating despite them.**

This usually requires some form of redundancy.

For example, having three API servers instead of one gives us redundancy at the application-server level.

But redundancy alone doesn't automatically make a system fault tolerant.

Suppose you have three API servers but all three depend on one database:

```text
        ┌── Server 1 ──┐
        ├── Server 2 ──┼── Database ❌
        └── Server 3 ──┘
```

The API servers can survive individual failures, but the database is still a single point of failure.

This introduces another important concept:

> **A distributed system can contain multiple components, but if one critical component has no alternative, that component can still become a single point of failure.**

We'll study this much more deeply later.

---

# Durability

Durability is primarily about **data**.

Durability means that once data has been successfully stored, it should **remain stored and not be lost**, even if something fails.

Imagine a payment system saying:

> "Your payment was successfully recorded."

but then the database crashes and the payment disappears.

That's a durability problem.

This is different from availability.

A database might be temporarily unavailable:

```text
Database ❌
```

but when it comes back, all previously committed data is still there.

That's poor availability during the outage, but potentially good durability.

Conversely, a database might remain online but lose committed data because of a storage failure.

That's an availability success but a durability failure.

So:

**Availability:**  
> Can I access the data/service?

**Durability:**  
> Will my committed data still exist?

This distinction becomes extremely important when we discuss databases, backups, replication, and object storage.

---

# Putting the terms together

At this point, we have several properties that sound similar but answer different questions:

| Property | Main question |
|---|---|
| **Scalability** | Can the system handle increasing workload? |
| **Availability** | Is the system usable when needed? |
| **Reliability** | Does it continue behaving correctly over time? |
| **Performance** | How quickly/efficiently does it perform? |
| **Fault tolerance** | Can it continue operating despite component failures? |
| **Durability** | Will committed data survive failures? |

These properties are related, but **none of them is simply another name for one of the others**.

For example, adding more API servers can improve both scalability and availability, but for different reasons.

Replication can improve fault tolerance and durability, but replication itself introduces consistency and synchronization problems.

Caching can improve performance and reduce database load, which can indirectly help availability, but a cache doesn't automatically make a system reliable or durable.

This is the kind of reasoning we want to develop throughout this curriculum.

---

# Why are distributed systems difficult?

This is probably the most important part of this lesson.

If multiple machines are cooperating, they need to communicate.

And communication happens over a **network**.

A function call inside one process is fundamentally different from:

```text
Server A
   ↓
 Network
   ↓
Server B
```

When Server A calls Server B, many things can go wrong.

Server B might crash.

The network might fail.

The request might arrive very late.

The response might arrive very late.

The request might reach Server B, Server B might successfully perform the operation, and then the response might get lost.

Now Server A has a difficult problem:

> **Did Server B perform the operation or not?**

That single question leads to many distributed-systems problems.

For example, suppose:

```text
Client → Payment Service
```

The payment service charges the card successfully.

But the response is lost.

The client sees:

```text
Timeout
```

Should the client retry?

If it retries, could the customer be charged twice?

If it doesn't retry, could the payment remain incomplete?

Now we need concepts such as **timeouts, retries, idempotency, duplicate detection, message delivery guarantees, replication, failover, and consistency**.

We'll learn each of those later, in the correct order.

The fundamental problem is this:

> **In a single-machine system, many operations happen within one machine that you control directly. In a distributed system, independent machines must coordinate through an unreliable network while each machine can fail independently.**

That's why distributed systems are difficult.

---

# The mental model I want you to keep

Don't think of distributed systems as:

> "An application with lots of servers."

Think of them as:

> **Multiple independent computers cooperating to provide a service, where communication happens over a network and individual components can fail independently.**

From that definition, most of the complexity follows naturally.

We distribute systems because one machine may not provide enough **capacity**, **performance**, **availability**, or **geographical reach**.

But distributing the system introduces **network communication, independent failures, coordination, synchronization, and partial failure**.

That is the central trade-off.

---

## Lesson recap

You should now be comfortable distinguishing:

- **Distributed system** → multiple independent computers cooperating.
- **Scalability** → ability to handle increasing workload by adding resources.
- **Availability** → ability to remain usable when requested.
- **Reliability** → ability to keep behaving correctly over time.
- **Performance** → how quickly and efficiently the system performs.
- **Fault tolerance** → ability to continue operating despite component failures.
- **Durability** → ability to preserve committed data despite failures.

And the fundamental reason distributed systems are difficult is **coordination between independent machines over a network where failures can occur independently**.
