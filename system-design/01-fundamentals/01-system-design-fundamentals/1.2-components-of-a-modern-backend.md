# 1.2 Components of a Modern Backend

In 1.1, we established that a distributed system consists of multiple independent computers cooperating to provide a service.

Now we need to understand the **building blocks that those computers and services provide**.

We are **not designing a system yet**. The goal of this chapter is simply to understand:

> **What does each component do, and why would a backend need it?**

A modern backend may contain many of these components, but **not every system needs all of them**.

---

## 1. Client

The **client** is the software that interacts with your backend on behalf of the user.

Examples include:

- a web browser
- a mobile application
- a desktop application
- another backend service

Suppose you open YouTube in your browser.

The browser is the client.

When you click a video, the client needs to communicate with YouTube's backend to obtain information and eventually the video content.

Conceptually:

```text
Client
   ↓
Backend
```

The client is therefore generally **outside the backend itself**.

Its job is to:

1. collect input from the user,
2. send requests,
3. receive responses,
4. present the results.

For example, your browser might send:

```http
GET /videos/123
```

The backend processes that request and returns data.

The client doesn't normally connect directly to the database. It communicates through the backend's exposed interfaces.

---

# 2. DNS

Before a client can communicate with a server, it needs to know **where to send the request**.

Humans use names such as:

```text
youtube.com
```

Computers ultimately communicate using IP addresses.

**DNS (Domain Name System)** translates domain names into information that allows the client to locate the appropriate service.

Conceptually:

```text
youtube.com
     ↓
   DNS
     ↓
IP address / service destination
```

So when your browser wants to communicate with:

```text
https://example.com
```

it first needs to resolve `example.com`.

DNS exists primarily because we don't want users and applications to have to remember or hard-code IP addresses.

There is another important property we'll encounter later:

**DNS can also participate in traffic routing.**

For example, a large global service may have infrastructure in several geographic regions. DNS can help direct users toward an appropriate endpoint.

We don't need to go deeper into DNS routing yet. For now, remember:

> **DNS maps human-friendly domain names to destinations that clients can connect to.**

---

# 3. Load Balancer

Suppose our backend has one API server:

```text
Client
   ↓
API Server
```

Now suppose we have ten API servers.

The client shouldn't have to know:

> "Which of these ten servers should I call?"

Instead, we put a **load balancer** in front of them.

```text
                 ┌── API Server 1
Client → Load Balancer ├── API Server 2
                 └── API Server 3
```

The load balancer receives incoming requests and decides **which backend server should handle each request**.

For example:

```text
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1
```

This is called **load balancing**.

Why does it exist?

Primarily because we may have multiple backend instances and need to distribute incoming traffic among them.

It can also detect unhealthy servers and stop sending traffic to them.

So a load balancer provides two important capabilities:

> **Traffic distribution and health-aware routing.**

We'll study load balancing in considerably more detail in Module 2.

---

# 4. API Gateway

An **API gateway** is another component that sits at the edge of a backend and acts as a controlled entry point for API requests.

It can handle **cross-cutting concerns** that apply to many APIs.

For example:

- authentication
- authorization
- rate limiting
- request routing
- TLS termination
- request/response policies
- logging
- API versioning

Consider a backend exposing several services:

```text
                    ┌── User Service
Client → API Gateway ├── Order Service
                    └── Payment Service
```

Instead of exposing every internal service directly to clients, the gateway can provide a common entry point.

The important distinction for now is:

> **A load balancer primarily distributes traffic among instances. An API gateway primarily provides an API entry point and applies cross-cutting API concerns.**

They can sometimes overlap in functionality, and in real architectures they may be implemented together or placed in different layers.

We will study API gateways more carefully later, after we understand load balancing.

---

# 5. API Server

The **API server** is where the application's backend logic is executed in response to client requests.

For example:

```text
Client
   ↓
API Server
```

A client might send:

```http
POST /orders
```

The API server could then:

1. authenticate the user,
2. validate the request,
3. execute business logic,
4. read or write data,
5. return a response.

For your .NET background, an ASP.NET Core application exposing controllers or minimal APIs is a typical API server.

The API server is therefore where we normally find **application/business logic**.

It might communicate with several other backend components:

```text
                ┌── Database
                │
Client → API Server ── Cache
                │
                └── Message Queue
```

Notice that the API server itself isn't necessarily where all the data lives or where every piece of work happens.

It often **coordinates** other components.

---

# 6. Database

A **database** provides persistent storage for structured application data.

For example, an e-commerce application might store:

```text
Users
Orders
Products
Payments
```

A relational database such as PostgreSQL or SQL Server might contain tables representing those entities.

The important characteristic is **persistence**.

If your API server restarts:

```text
API Server ❌
```

the application's data should still exist.

The database therefore acts as a persistent source of data.

For example:

```text
API Server
    ↓
Database
    ↓
Users / Orders / Products
```

The API server usually interacts with the database rather than exposing the database directly to clients.

We'll study databases in much more depth in Module 4, including replication, indexes, transactions, consistency, and scaling.

---

# 7. Cache

A **cache stores data temporarily so that it can be retrieved faster than obtaining it from the original source**.

Suppose an API repeatedly needs the same product information.

Without a cache:

```text
API Server → Database
             ↓
          Product
```

If thousands of requests repeatedly ask for the same product, the database has to repeatedly perform the work.

With a cache:

```text
API Server → Cache
             ↓
          Product
```

If the data is already in the cache, the API can return it without querying the database.

This gives us two concepts:

**Cache hit:** the requested data is already in the cache.

**Cache miss:** the requested data isn't there, so the application must obtain it from the original source.

Caching can therefore improve:

- latency
- throughput
- database load

But there's an important trade-off:

> **Cached data may become stale.**

If the database says:

```text
Price = $100
```

but the cache still contains:

```text
Price = $90
```

the application may temporarily return the old value.

Caching is therefore not simply "make everything faster." It introduces questions about **expiration and consistency**, which we'll study in Module 3.

---

# 8. Object Storage

A traditional database is good for application data such as:

```text
User
Order
Product
```

But applications also need to store very large files:

- videos
- images
- PDFs
- backups
- audio
- datasets

This is where **object storage** is useful.

Examples include Amazon S3, Azure Blob Storage, and Google Cloud Storage.

Instead of storing a 5 GB video inside a database row, we can store the actual file in object storage.

Conceptually:

```text
API Server
    ↓
Object Storage
    ↓
video.mp4
```

Object storage organizes data as **objects**, typically identified by an object key.

For example:

```text
videos/123/original.mp4
```

The backend database can store information *about* the object:

```text
Video
----------------------
id = 123
title = "My Video"
object_key = videos/123/original.mp4
```

The database stores the metadata and reference; object storage stores the large binary data.

This distinction becomes particularly important for systems such as YouTube, image platforms, document systems, and backup systems.

---

# 9. Message Queue

Now let's consider a different problem.

Suppose an API receives an image upload.

After receiving it, the system needs to:

- resize it,
- generate thumbnails,
- scan it,
- update metadata.

Doing all of that synchronously might make the user's request take several seconds.

Instead, the API can put a **message describing the work** into a message queue.

```text
API Server
    ↓
Message Queue
    ↓
Worker
```

The API can respond quickly:

> "Your upload has been accepted."

The worker can process the job afterward.

A queue therefore allows work to be **decoupled from the request that initiated it**.

It is particularly useful when:

- work takes a long time,
- work doesn't need to happen immediately,
- processing needs to happen asynchronously,
- consumers need to process work at their own rate.

A queue also provides a place where pending work can wait if consumers temporarily cannot keep up.

We'll study queues properly in Module 6.

---

# 10. Event Stream

An **event stream** is related to a message queue, but it solves a somewhat different problem.

Imagine an order system produces this event:

```text
OrderCreated
```

Several independent systems may be interested in that event:

```text
                    ┌── Analytics
                    │
Order Service → Event Stream ── Notifications
                    │
                    └── Recommendation System
```

The event stream allows those consumers to process the event independently.

A major characteristic of an event stream is that events are generally **retained for some period of time**, allowing consumers to process them and, depending on the system, replay them later.

Kafka is a well-known example of an event-streaming platform.

A queue is commonly thought of as:

> **"Here is work that needs to be processed."**

An event stream is commonly thought of as:

> **"This thing happened; interested systems can consume that event."**

The distinction isn't absolute—technologies can support overlapping patterns—but this mental model is useful.

We'll go much deeper into queues, Kafka, partitions, consumers, offsets, ordering, and delivery guarantees later.

---

# 11. Search Engine

A database can answer queries such as:

```sql
SELECT *
FROM Products
WHERE category = 'Laptop';
```

But applications often need much more sophisticated search.

For example, a user might type:

> `wireless noise cancelling headphones`

and expect results based on:

- words appearing in titles
- descriptions
- relevance
- synonyms
- ranking
- typo tolerance
- filters
- facets

A dedicated **search engine** is optimized for this type of workload.

Examples include Elasticsearch and OpenSearch.

Conceptually:

```text
             ┌── Database
API Server ──┤
             └── Search Engine
```

The database generally remains the authoritative source of application data.

The search engine contains a **search-optimized representation** of that data.

For example:

```text
Database
    ↓
Indexing process
    ↓
Search Engine
```

If the database changes, the search index may be updated asynchronously.

That means search results can temporarily lag behind the database.

This is another example of a **derived representation** rather than the original source of truth.

We'll study search systems later.

---

# 12. CDN

Finally, consider a website with users all over the world.

Suppose your actual server is located in the US:

```text
User in Germany ───────────────→ US server
User in Japan ────────────────→ US server
User in Australia ────────────→ US server
```

For large static files such as images, JavaScript files, videos, and other cacheable content, it may be inefficient for every user to retrieve everything directly from your origin servers.

A **CDN (Content Delivery Network)** places cached content at locations geographically closer to users.

Conceptually:

```text
                    ┌── CDN edge → User in Germany
Origin ── CDN ──────┼── CDN edge → User in Japan
                    └── CDN edge → User in Australia
```

If a user requests content that is already cached at a nearby CDN location, the CDN can serve it without contacting the origin server.

This can reduce:

- latency for users
- bandwidth consumed by origin servers
- load on origin infrastructure

CDNs are particularly useful for content that is **read frequently and changes relatively infrequently**.

For example, a video that millions of people watch doesn't need to be transferred from the origin server for every viewer. The CDN can serve cached video data from edge locations.

We'll study CDN caching separately in Module 3.

# How these components fit together conceptually

We're **not designing a system yet**, but it's useful to see what roles these components occupy.

A request might conceptually pass through several of them:

```text
Client
   ↓
DNS
   ↓
Load Balancer
   ↓
API Gateway
   ↓
API Server
   ├──→ Cache
   ├──→ Database
   ├──→ Object Storage
   ├──→ Message Queue
   ├──→ Event Stream
   └──→ Search Engine

CDN
   ↕
Origin / Object Storage
```

This is **not a required architecture**.

A small application might only have:

```text
Client → API Server → Database
```

A much larger system might eventually need many of these components.

The important thing is to understand **the problem each component solves**, rather than memorizing a standard architecture.

---

## One important distinction

There are three different ideas that are easy to mix up:

**Database:**  
> "This is my application's persistent data."

**Cache:**  
> "This is a temporary copy of data that I can retrieve quickly."

**Search engine:**  
> "This is a search-optimized representation of data."

And similarly:

**Message queue:**  
> "This work needs to be processed."

**Event stream:**  
> "This event happened, and multiple consumers may be interested in it."

These distinctions will become much more important when we start designing systems.

---

## Lesson recap

You should now have a basic mental model for each component:

- **Client** — initiates interaction with the backend.
- **DNS** — resolves a domain name to a destination.
- **Load balancer** — distributes incoming traffic among backend instances.
- **API gateway** — provides an API entry point and handles cross-cutting edge concerns.
- **API server** — executes application/business logic and coordinates backend operations.
- **Database** — persistently stores application data.
- **Cache** — temporarily stores frequently accessed data for faster retrieval.
- **Object storage** — stores large files/blobs.
- **Message queue** — holds asynchronous work waiting to be processed.
- **Event stream** — records events that multiple consumers can independently process.
- **Search engine** — provides search-optimized indexing and retrieval.
- **CDN** — serves cacheable content from geographically distributed edge locations.

The key lesson isn't the list itself.

It's this:

> **Each component exists because it solves a particular problem that becomes difficult or inefficient to solve with the basic API-server-and-database model.**

That's the foundation we'll build on.
