# How to

- Start by saying: Before I design it, I'd like to clarify a few requirements
- Then ask: 
  - Function requirements
  - Non-functional requirements
- List the GET, POST, etc. API endpoints for the operations defined above in the functional requirements
- Now think about what data needs to be stored
  - In addition to the data required for the system, also mention that we could also have: created_at, expires_at, user_id, etc. 
- Once the data to be stored is discussed and finalized, determine the kind of database to be used. (Do not be specific about the flavor of db - SQL Server, or DynamoDB, etc.) Several decisions could determine that: 
  - Read heavy vs. Write heavy
  - Consistency guarantees
  - Relationships
  - Structure of data
- Now start drawing
  - Draw a client
  - Draw an API
  - Add a database
- That's your first version. Don't add Redis, Kafka, Kubernetes, 17 microservices, etc. 
- Determine whether caching could be introduced
  - If the system is read-heavy
- Now update the diagram with a cache sitting between API and database
  - Indicate cache hit
  - Indicate cache miss
- Now think about scale
- Discuss adding more API servers 
  - Scalability: to handle more load under pressure
  - Availability: if one server goes down, the other are still there to serve 
- That would mean adding a Load balancer between the client and API servers
- But now that you have added more servers, and possibly caching, we might need a distributed cache
  - So that each server does not have it's own cache
  - Maybe the requested item is in Server A's cache, but the request went to Server B
- Talk about reliability: If cache fails, the db still holds the data, and data can be served from it
- Observability (You don't need to say "Datadog" unless they ask what tooling you'd use.)
  - Metrics
    - request latency
    - requests per second
    - error rate
    - cache hit rate
    - database latency
  - Logs
    - failed redirects
    - invalid URLs
    - database errors
  - Traces (Useful when a request goes through: Load Balancer → API → Cache → Database)
- Now summarize your design, explaining how you'd start from simple elements, and then you add elements because they would help with a particular requirement

- Start simple
- Show that you understand the trade-offs.

And notice how many of the Immowelt JD keywords naturally appeared:

**scalability → reliability → availability → observability → automation → simplicity → trade-offs.**
