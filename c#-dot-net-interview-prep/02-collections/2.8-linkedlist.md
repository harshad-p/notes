# 2.8 `LinkedList<T>`

`LinkedList<T>` is a **doubly linked list**.

Unlike `List<T>`, which stores elements in a contiguous array, a linked list stores elements in separate nodes connected through references.

```text
+------+      +------+      +------+
|  A   | <--> |  B   | <--> |  C   |
+------+      +------+      +------+
   ^                              ^
   |                              |
 First                          Last
```

Each node knows about its neighboring nodes.

---

## 1. Creating a `LinkedList<T>`

```csharp
var numbers = new LinkedList<int>();

numbers.AddLast(10);
numbers.AddLast(20);
numbers.AddLast(30);
```

The structure is conceptually:

```text
First                         Last
  |                             |
  v                             v
+----+      +----+      +----+
| 10 | <--> | 20 | <--> | 30 |
+----+      +----+      +----+
```

You can also initialize it from an existing collection:

```csharp
var numbers = new LinkedList<int>(
    new[] { 10, 20, 30 }
);
```

---

## 2. `LinkedListNode<T>`

The individual elements are represented by `LinkedListNode<T>`.

```csharp
LinkedListNode<int> node = numbers.First!;
```

A node provides:

```csharp
node.Value
node.Next
node.Previous
```

For example:

```csharp
var first = numbers.First!;

Console.WriteLine(first.Value); // 10
Console.WriteLine(first.Next!.Value); // 20
Console.WriteLine(first.Next!.Next!.Value); // 30
```

Conceptually:

```text
        Next
  +--------------+
  |              v
+-----+      +-----+
| 10  | ---> | 20  |
+-----+      +-----+
   ^            |
   |            |
   +------------+
      Previous
```

---

## 3. `First` and `Last`

You can access the first and last nodes directly:

```csharp
LinkedListNode<int>? first = numbers.First;
LinkedListNode<int>? last = numbers.Last;
```

And access their values:

```csharp
int firstValue = numbers.First!.Value;
int lastValue = numbers.Last!.Value;
```

Both `First` and `Last` are **O(1)**.

---

## 4. `Count`

`Count` gives the number of nodes:

```csharp
Console.WriteLine(numbers.Count);
```

`Count` is **O(1)**.

The linked list maintains the count rather than traversing the list every time.

---

## 5. `AddFirst()`

Adds an element to the beginning.

```csharp
numbers.AddFirst(5);
```

Before:

```text
10 <-> 20 <-> 30
```

After:

```text
5 <-> 10 <-> 20 <-> 30
```

`AddFirst()` is **O(1)**.

---

## 6. `AddLast()`

Adds an element to the end.

```csharp
numbers.AddLast(40);
```

Result:

```text
5 <-> 10 <-> 20 <-> 30 <-> 40
```

`AddLast()` is **O(1)** because the list maintains a reference to the last node.

---

## 7. `AddBefore()` and `AddAfter()`

This is one of the main advantages of `LinkedList<T>`.

First, obtain a node:

```csharp
var node = numbers.Find(20)!;
```

Then:

```csharp
numbers.AddBefore(node, 15);
numbers.AddAfter(node, 25);
```

Result:

```text
5 <-> 10 <-> 15 <-> 20 <-> 25 <-> 30 <-> 40
```

Once you already have the node, inserting before or after it is **O(1)**.

This is an important distinction:

```text
Find the node       -> O(n)
Insert around node  -> O(1)
```

So saying "`LinkedList<T>` insertion is O(1)" without qualification is incomplete.

---

## 8. `Remove()`

You can remove a specific node:

```csharp
var node = numbers.Find(20)!;

numbers.Remove(node);
```

If you already have the node, removal is **O(1)**.

You can also remove by value:

```csharp
numbers.Remove(20);
```

But this first has to find the node.

Therefore:

```text
Remove(node)   -> O(1)
Remove(value)  -> O(n)
```

---

## 9. `RemoveFirst()` and `RemoveLast()`

```csharp
numbers.RemoveFirst();
numbers.RemoveLast();
```

Both are **O(1)**.

The list already knows where its first and last nodes are.

---

## 10. `Find()`

```csharp
var node = numbers.Find(30);
```

The list has to traverse the nodes until it finds the value.

Therefore:

```text
Find() -> O(n)
```

This is one of the major differences from a `Dictionary<TKey,TValue>` or `HashSet<T>`.

---

## 11. `FindLast()`

You can search from the end:

```csharp
var node = numbers.FindLast(30);
```

This is still **O(n)** in the worst case.

---

## 12. `Contains()`

```csharp
bool exists = numbers.Contains(20);
```

`Contains()` requires traversal.

```text
Contains() -> O(n)
```

---

## 13. `Clear()`

```csharp
numbers.Clear();
```

Removes all nodes.

Afterward:

```csharp
numbers.Count == 0
```

The operation is generally **O(n)** because the nodes need to be cleared.

---

## 14. Does `LinkedList<T>` have Capacity?

No.

This is an important contrast with `List<T>`, `Queue<T>`, and `Stack<T>`.

`LinkedList<T>` does **not** have:

```csharp
Capacity
```

or:

```csharp
EnsureCapacity()
```

Why?

Because it doesn't maintain a single dynamically resized internal array.

Each element is stored in its own node.

Conceptually:

```text
List<T>

[ A ][ B ][ C ][   ][   ]
       one array


LinkedList<T>

[A] <-> [B] <-> [C]
 |       |       |
node    node    node
```

Therefore, there is no concept of preallocating space for 1,000 elements in a `LinkedList<T>`.

---

## 15. Memory overhead

This is one of the biggest disadvantages of `LinkedList<T>`.

Each element requires a separate node containing:

```text
Value
Next reference
Previous reference
```

Conceptually:

```text
+-------------------+
| Value             |
| Next              |
| Previous          |
+-------------------+
```

So compared with an array-backed collection, there is additional memory overhead.

There is also less cache locality because nodes may be located in different areas of memory.

This can make `LinkedList<T>` slower in practice even when its theoretical complexity looks attractive.

---

## 16. `List<T>` vs `LinkedList<T>`

This is an important interview comparison.

| Operation | `List<T>` | `LinkedList<T>` |
|---|---:|---:|
| Index access | O(1) | O(n) |
| Search | O(n) | O(n) |
| Add at end | O(1) amortized | O(1) |
| Insert at beginning | O(n) | O(1) |
| Remove at beginning | O(n) | O(1) |
| Insert with known position/node | O(n) | O(1) |
| Remove with known node | O(n) | O(1) |
| Memory locality | Good | Poor |
| Capacity | Yes | No |

The critical difference is:

```text
List<T>
    -> fast random access
    -> contiguous storage
    -> good cache locality

LinkedList<T>
    -> fast insertion/removal when node is known
    -> no random access
    -> additional node overhead
```

---

## 17. Why not always use `LinkedList<T>`?

Because its theoretical O(1) insertion/removal can be misleading.

Suppose you want to insert `50` after `40`.

With a linked list:

```text
Find 40 -> O(n)
Insert 50 -> O(1)
```

Overall:

```text
O(n)
```

If you don't already have the node, you often lose the theoretical advantage.

And `List<T>` generally has better memory locality and lower per-element overhead.

Therefore, in modern application code, `List<T>` is often preferable unless you have a specific reason to use a linked list.

---

## 18. Interfaces implemented by `LinkedList<T>`

`LinkedList<T>` implements:

```text
ICollection<T>
IEnumerable<T>
IEnumerable
ICollection
```

It does **not** implement `IList<T>`.

That's important.

Why?

Because `IList<T>` implies index-based access:

```csharp
list[5]
```

But `LinkedList<T>` doesn't support efficient index-based access.

You cannot do:

```csharp
numbers[5]; // Not supported
```

Instead, you navigate through nodes:

```csharp
var node = numbers.First;

node = node!.Next;
```

---

## 19. Traversing a `LinkedList<T>`

The normal approach is simply:

```csharp
foreach (var number in numbers)
{
    Console.WriteLine(number);
}
```

Or manually using nodes:

```csharp
var current = numbers.First;

while (current != null)
{
    Console.WriteLine(current.Value);
    current = current.Next;
}
```

Reverse traversal is possible because it's doubly linked:

```csharp
var current = numbers.Last;

while (current != null)
{
    Console.WriteLine(current.Value);
    current = current.Previous;
}
```

---

## 20. When is `LinkedList<T>` actually useful?

Good examples include situations where:

- You already have references to nodes.
- You frequently insert/remove around known nodes.
- You need efficient operations at both ends.
- You need stable node references during modifications.
- The data structure naturally maps to linked nodes.

For example:

```text
A <-> B <-> C <-> D
         ^
         |
       node
```

If you already have the node `C`, inserting something after it is cheap:

```text
A <-> B <-> C <-> X <-> D
```

No shifting of all subsequent elements is necessary.

---

## 21. When should you NOT use it?

Avoid `LinkedList<T>` when you primarily need:

- Random/indexed access
- Fast searching
- Compact memory usage
- Good cache locality
- General-purpose collection storage

For those scenarios, `List<T>` is usually a better choice.

## Interview questions

### Why is accessing an element by index O(n)?

Because a linked list has no direct index-to-memory mapping.

To access the element at position 100, you have to traverse the nodes.

```text
First
  |
  v
[0] -> [1] -> [2] -> ... -> [100]
```

Therefore:

```text
list[100] -> O(n)
```

---

### Why can insertion be O(1)?

If you already have a reference to the relevant `LinkedListNode<T>`, the list only needs to update a few references.

```text
Before:

A <-> B <-> C


Insert X after B:

A <-> B <-> X <-> C
```

No elements need to be shifted.

---

### Is inserting into a `LinkedList<T>` always O(1)?

No.

That's a common interview trap.

If you first need to find the insertion point:

```text
Find node -> O(n)
Insert     -> O(1)
```

the overall operation is:

```text
O(n)
```

---

### Why doesn't `LinkedList<T>` have Capacity?

Because it doesn't use a single dynamically resized array. Each element is stored in a separate node, so there is no internal array capacity to manage.

---

### Why might `List<T>` be faster than `LinkedList<T>` even for operations where both appear to be O(n)?

Because `List<T>` provides better memory locality and lower per-element overhead. Its contiguous storage is generally more CPU-cache-friendly.

---

## What you should remember

For an interview:

> `LinkedList<T>` is a doubly linked list where each element is stored in a node containing the value and references to the previous and next nodes. It provides O(1) insertion and removal when the relevant node is already known, but searching and indexed access are O(n). Unlike `List<T>`, it has no Capacity because it doesn't use a dynamically resized array. It implements `ICollection<T>` and `IEnumerable<T>`, but not `IList<T>`.

## Follow-ups

> Are there more ways to initialize a LinkedList?

Yes. There are additional ways to initialize `LinkedList<T>`

### 1. Empty constructor

```csharp
var numbers = new LinkedList<int>();
```

Most basic form.

---

### 2. Initialize from `IEnumerable<T>`

```csharp
var numbers = new LinkedList<int>(
    new[] { 10, 20, 30 }
);
```

The constructor accepts an `IEnumerable<T>`, so many enumerable sources can be used:

```csharp
var numbers = new LinkedList<int>(
    new List<int> { 10, 20, 30 }
);
```

```csharp
var numbers = new LinkedList<int>(
    Enumerable.Range(1, 5)
);
```

---

### 3. Collection initializer

You can also use C# collection-initializer syntax:

```csharp
var numbers = new LinkedList<int>
{
    10,
    20,
    30
};
```

This is essentially syntactic sugar for adding the elements individually.

Conceptually:

```csharp
var numbers = new LinkedList<int>();

numbers.AddLast(10);
numbers.AddLast(20);
numbers.AddLast(30);
```

---

### 4. Copy from another `LinkedList<T>`

Since `LinkedList<T>` implements `IEnumerable<T>`, you can create another linked list from it:

```csharp
var original = new LinkedList<int>
{
    10,
    20,
    30
};

var copy = new LinkedList<int>(original);
```

This creates a **new linked list with the same values**.

It does not reuse the original nodes.
