# 2.2: `List<T>`

A `List<T>` is a resizable, array-backed collection. It stores elements of type `T` and lets you add or remove elements without manually creating a new array each time.

Use a `List<T>` when you need an ordered collection whose size can change.

`List<T>` implements:

* `IList<T>` — provides indexed access and list operations.

* `ICollection<T>` — provides basic collection operations such as `Add`, `Remove`, and `Count`.

* `IEnumerable<T>` — supports iteration.

* `IReadOnlyList<T>` — provides read-only indexed access through that interface.

* `IReadOnlyCollection<T>` — provides read-only collection access and `Count`.

It also implements non-generic interfaces such as `IList`, `ICollection`, and `IEnumerable`.

## 1. Creating and initializing a list

C#

```
List<int> numbers = new List<int>();

List<int> scores = new List<int> { 10, 20, 30 };

List<string> names = ["Alice", "Bob", "Charlie"]; // C# 12
```

You can also specify an initial capacity:

C#

```
List<int> numbers = new List<int>(100);
```

This creates an empty list with capacity for at least 100 elements. It does not create a list containing 100 elements.

## 2. `Count` vs `Capacity`

This is one of the most important concepts to understand about `List<T>`.

* `Count` is the number of elements currently stored.

* `Capacity` is how many elements the internal storage array can hold before it needs to grow.

C#

```
List<int> numbers = new List<int>();

Console.WriteLine(numbers.Count);    // 0
Console.WriteLine(numbers.Capacity); // 0

numbers.Add(10);
numbers.Add(20);
numbers.Add(30);

Console.WriteLine(numbers.Count);    // 3
Console.WriteLine(numbers.Capacity); // At least 3
```

A list internally maintains an array. When you add an element and the array has no free space, the list allocates a larger array and copies the existing elements into it.

Conceptually:

```
Count = 3
Capacity = 4

Internal array:
+----+----+----+------+
| 10 | 20 | 30 | free |
+----+----+----+------+
```

The exact growth strategy is an implementation detail. Don't rely on a particular capacity multiplier as a guaranteed API behavior.

You can also set the capacity:

C#

```
numbers.Capacity = 20;
```

You cannot set `Capacity` below `Count`.

## 3. Common operations

### Add and insert

C#

```
List<string> names = ["Alice", "Charlie"];

names.Add("David");
// Alice, Charlie, David

names.Insert(1, "Bob");
// Alice, Bob, Charlie, David
```

`Add()` appends to the end. `Insert()` places an element at a specific index and shifts later elements to make room.

### Access and update

C#

```
Console.WriteLine(names[0]); // Alice

names[0] = "Alex";
```

Like arrays, lists use zero-based indexing.

### Remove elements

C#

```
names.Remove("Charlie"); // Removes the first matching element

names.RemoveAt(0);       // Removes the element at index 0

names.RemoveRange(0, 2); // Removes 2 elements starting at index 0

names.Clear();           // Removes all elements
```

`Remove()` returns `true` if it found and removed an element, otherwise `false`.

`RemoveAt()` and `RemoveRange()` throw an exception if the specified index or range is invalid.

### Search

C#

```
List<int> numbers = [10, 20, 30, 20];

Console.WriteLine(numbers.Contains(20)); // true
Console.WriteLine(numbers.IndexOf(20));  // 1
Console.WriteLine(numbers.LastIndexOf(20)); // 3
```

You can also search using a condition:

C#

```
int firstEven = numbers.Find(n => n % 2 == 0);

List<int> evenNumbers = numbers.FindAll(n => n % 2 == 0);
```

`Find()` returns the first matching element, or the default value of `T` if no match is found. For value types, that may be `0`; for reference types, it is usually `null`.

## 4. Iterating over a list

C#

```
List<string> names = ["Alice", "Bob", "Charlie"];

foreach (string name in names)
{
    Console.WriteLine(name);
}
```

You can also use a `for` loop when you need the index:

C#

```
for (int i = 0; i < names.Count; i++)
{
    Console.WriteLine($"{i}: {names[i]}");
}
```

Avoid structurally modifying a list during a `foreach` iteration. For example, adding or removing elements generally invalidates the enumerator and causes an `InvalidOperationException` on a subsequent iteration step.

If you need to remove matching elements, use methods such as `RemoveAll()`:

C#

```
List<int> numbers = [1, 2, 3, 4, 5, 6];

numbers.RemoveAll(n => n % 2 == 0);

// 1, 3, 5
```

## 5. How `List<T>` grows internally

Imagine a list with capacity 4:

```
Count = 4
Capacity = 4

+----+----+----+----+
| 10 | 20 | 30 | 40 |
+----+----+----+----+
```

Now you add another element:

C#

```
numbers.Add(50);
```

The internal array has no room. The list must allocate a larger array, copy the existing elements, and place the new element into it.

Conceptually:

```
Old array:
+----+----+----+----+
| 10 | 20 | 30 | 40 |
+----+----+----+----+

New array:
+----+----+----+----+----+----+----+----+
| 10 | 20 | 30 | 40 | 50 | free | free | free |
+----+----+----+----+----+----+----+----+
```

The old array becomes eligible for garbage collection when nothing references it anymore.

This explains why `Add()` is usually fast but can occasionally be expensive when the list needs to grow.

## 6. Time complexity

| Operation                           | Typical time complexity             | Reason                                          |
| ----------------------------------- | ----------------------------------- | ----------------------------------------------- |
| Access by index                     | O(1)                                | Direct array indexing                           |
| Update by index                     | O(1)                                | Direct array indexing                           |
| `Add()`                             | Amortized O(1)                      | Usually appends; occasional resizing costs O(n) |
| `Insert()` at beginning or middle   | O(n)                                | Elements need to shift                          |
| `RemoveAt()` at beginning or middle | O(n)                                | Elements need to shift                          |
| `Remove()`                          | O(n)                                | Searches for the item, then may shift elements  |
| `Contains()`                        | O(n)                                | Linear search                                   |
| `IndexOf()`                         | O(n)                                | Linear search                                   |
| `Clear()`                           | O(n) for reference-containing lists | References may need clearing                    |
| `Sort()`                            | O(n log n)                          | Comparison-based sorting                        |

What does amortized O(1) mean for `Add()`?

Most individual additions take O(1). Occasionally, an addition triggers allocation and copying, which takes O(n).

But if you perform many additions, the total cost averaged across all those additions is O(1) per addition, under the usual dynamic-array growth strategy.

This is why we say `Add()` is amortized O(1), not guaranteed O(1) for every call.

## 7. `List<T>` vs array

| Feature         | Array                                              | `List<T>`                 |
| --------------- | -------------------------------------------------- | ------------------------- |
| Size            | Fixed after creation                               | Resizable                 |
| Index access    | O(1)                                               | O(1)                      |
| Append          | Not directly supported                             | `Add()`                   |
| Insert/remove   | Requires manual shifting or creating another array | Built-in methods          |
| Storage         | Array                                              | Internal array            |
| Memory          | No extra list capacity management                  | May have unused capacity  |
| Best suited for | Fixed-size data                                    | Changing-size collections |

Both arrays and lists offer fast index-based access because a list uses an array internally.

The main difference is that `List<T>` manages resizing and provides convenient operations.

## 8. Other useful `List<T>` APIs

| Method or property | Purpose                                                 |
| ------------------ | ------------------------------------------------------- |
| `AddRange()`       | Adds multiple elements                                  |
| `InsertRange()`    | Inserts multiple elements at an index                   |
| `RemoveAll()`      | Removes all elements matching a condition               |
| `Find()`           | Finds the first matching element                        |
| `FindAll()`        | Returns all matching elements in a new list             |
| `FindIndex()`      | Finds the index of a matching element                   |
| `Exists()`         | Checks whether any element matches a condition          |
| `TrueForAll()`     | Checks whether every element matches a condition        |
| `Sort()`           | Sorts the list in place                                 |
| `Reverse()`        | Reverses the list in place                              |
| `ToArray()`        | Creates a new array containing the list's elements      |
| `TrimExcess()`     | Reduces capacity when there is substantial unused space |
| `EnsureCapacity()` | Ensures a minimum capacity                              |
| `AsReadOnly()`     | Returns a read-only wrapper over the list               |

One subtle point: `AsReadOnly()` does not make the original list immutable. It prevents modification through the returned wrapper, but changes to the original list are visible through that wrapper.

## 9. Interview questions and scenarios

Q1. Why is `List<T>.Add()` considered amortized O(1)?

Because most additions use existing capacity and take constant time. Occasional resizing requires copying elements, but the average cost across many additions remains constant per operation.

Q2. What is the difference between `Count` and `Capacity`?

`Count` is the number of elements in the list. `Capacity` is the size of its internal storage array.

Q3. What happens when you insert an element at index 0?

Existing elements shift one position to the right to make room. This takes O(n) time.

Q4. When would you use an array instead of `List<T>`?

When the number of elements is fixed, when you need a simple fixed-size structure, or when an API specifically requires an array. A list is more convenient when the collection changes in size.

Q5. What happens if you modify a list during `foreach`?

Structural modifications such as adding or removing elements invalidate the enumerator. A subsequent iteration step typically throws `InvalidOperationException`. Use a `for` loop carefully, iterate over a snapshot, or use methods such as `RemoveAll()` depending on the task.

Q6. If a list has 1,000 elements and capacity 2,000, does adding an element allocate a new array?

No. There is already sufficient capacity, so the element can be appended without resizing the internal array.

## Follow-ups

> Can you add an element to an empty list using indexing? Eg.: list[1000] = 1000

No. This will throw an `ArgumentOutOfRangeException`:

C#

```
List<int> numbers = [];

numbers[1000] = 1000; // Exception
```

The reason is that indexing accesses or replaces an existing element; it doesn't add a new one.

An empty list has:

C#

```
numbers.Count    // 0
numbers.Capacity // Usually 0 for a newly created empty list
```

Even if you create a list with enough capacity, you still can't access an index beyond its current `Count`.

C#

```
List<int> numbers = new List<int>(2000);

numbers[1000] = 1000; // Still throws
```

Here, the list has storage capacity for at least 2,000 elements, but it still contains zero elements.

To add an element, use `Add()`:

C#

```
numbers.Add(1000);
```

Now the element is at index `0`, not index `1000`.

If you specifically need an element at index `1000`, you must first populate the list with at least 1,001 elements. For example:

C#

```
List<int> numbers = Enumerable.Repeat(0, 1001).ToList();

numbers[1000] = 1000;
```

Now index `1000` exists and can be updated.

The distinction is:

* `Capacity` determines how much storage is available.

* `Count` determines how many elements currently exist.

* Valid indexes range from `0` to `Count - 1`.

> What does `EnsureCapacity()` do?

`EnsureCapacity()` makes sure a list's internal array has at least the requested capacity.

C#

```
List<int> numbers = [];

int capacity = numbers.EnsureCapacity(100);

Console.WriteLine(capacity);        // At least 100
Console.WriteLine(numbers.Count);   // 0
Console.WriteLine(numbers.Capacity); // At least 100
```

Notice that it doesn't add any elements. It only ensures enough internal storage.

This is useful when you know in advance that you're going to add many elements.

For example:

C#

```
List<int> numbers = [];

numbers.EnsureCapacity(10_000);

for (int i = 0; i < 10_000; i++)
{
    numbers.Add(i);
}
```

Without `EnsureCapacity()`, the list may need to resize several times as elements are added. With it, the list can use the reserved capacity for those additions without growing its internal array.

A few important details:

* If the list already has enough capacity, `EnsureCapacity()` doesn't need to grow it.

* It returns the resulting capacity.

* If it needs to grow, it may allocate a new array and copy existing elements.

* It doesn't shrink the list if the requested capacity is smaller than its current capacity.

You can think of it as reserving storage ahead of time to avoid repeated resizing.

> How does `List<T>` resize? Is it at 75% capacity like Java?

No. In .NET, `List<T>` generally grows when it runs out of capacity, not when it reaches a percentage threshold.

For example, suppose the list has a capacity of 4:

C#

```
List<int> numbers = new List<int>(4);

numbers.Add(10);
numbers.Add(20);
numbers.Add(30);
numbers.Add(40);
```

At this point:

```
Count = 4
Capacity = 4
```

When you add the fifth element:

C#

```
numbers.Add(50);
```

The list needs more storage, so it grows its internal array.

In current .NET implementations, the usual growth pattern is approximately doubling the capacity:

```
Capacity:  0 → 4 → 8 → 16 → 32 → 64
```

The initial capacity is typically 4 when a default-constructed empty list first needs storage. If a requested minimum capacity is larger than the usual doubled capacity, the list can grow directly to that minimum instead.

### Example of the growth process

Suppose the capacity is 4 and the list already contains four elements.

```
Before adding the fifth element:

Count = 4
Capacity = 4

Internal array:
+----+----+----+----+
| 10 | 20 | 30 | 40 |
+----+----+----+----+
```

When adding `50`:

1. The list detects that the internal array is full.

2. It allocates a larger array, usually with twice the previous capacity.

3. It copies the existing elements into the new array.

4. It adds the new element.
```
   After adding the fifth element:

   Count = 5
   Capacity = 8

   Internal array:
   +----+----+----+----+----+----+----+----+
   | 10 | 20 | 30 | 40 | 50 |    |    |    |
   +----+----+----+----+----+----+----+----+
```
The old array is no longer used by the list and becomes eligible for garbage collection once no references to it remain.

### Comparison with Java

The commonly used growth strategies differ:

| Feature                                        | .NET `List<T>`                | Java `ArrayList`              |
| ---------------------------------------------- | ----------------------------- | ----------------------------- |
| Growth trigger                                 | When capacity is insufficient | When capacity is insufficient |
| Typical growth                                 | Approximately 2x              | Approximately 1.5x            |
| Fixed growth percentage threshold, such as 75% | No                            | No                            |
| Internal storage                               | Array                         | Array                         |

Java's `ArrayList` also generally grows when it runs out of capacity, rather than waiting for a 75% threshold. Its typical growth factor is around 1.5, not a 75% load-factor trigger.

### Why does doubling help performance?

Consider adding 1,000 elements one by one.

If the list resized for every addition, it could repeatedly copy a growing number of elements, resulting in O(n²) total copying work.

By increasing capacity geometrically, resizing happens less frequently. The total copying work over many appends is O(n), making the average cost per append amortized O(1).

One important interview detail: the exact growth factor is an implementation detail, not a guarantee of the `List<T>` API. It's useful to understand the current behavior, but don't write code that depends on capacity doubling.

Also remember that `EnsureCapacity()` lets you request enough capacity in advance, reducing the need for those intermediate resizing operations when you know approximately how many elements you'll add.

> If Count is 0, but Capacity is 1000, then what is the point of having so much capacity? Why can't I use indexing to insert anywhere within that capacity? I expect the runtime to create an internal array of size capacity. So if there is already an internal array of size capacity, why not allow inserting at any index within that capacity? Seems like it is only to ensure no re-allocation happens and be prepared beforehand.

Your understanding is correct: the main purpose of having extra capacity is to avoid reallocating the internal array as elements are added.

The distinction you're questioning is between the list's allocated storage and its logical contents. Let's look at why .NET keeps those separate.

### Why can't indexing use the entire capacity?

Suppose you create a list with capacity 1,000:

C#

```
List<int> numbers = new List<int>(1000);
```

Internally, the list has an array with room for 1,000 integers. But:

C#

```
numbers.Count    // 0
numbers.Capacity // 1000
```

The list treats only the first `Count` positions as actual elements.

Why? Because a list is designed to represent a sequence of existing elements, not a preallocated array of potential positions.

Consider this example:

C#

```
List<string> names = new List<string>(1000);
```

If indexing were allowed anywhere within capacity, what should `names[500]` return? Should the list contain 500 empty or `null` entries before it? Should those positions count as elements? Should iteration visit them?

By requiring `Count` to track actual elements, the list avoids ambiguity.

For example:

C#

```
List<int> numbers = new List<int>(1000);

numbers.Add(10);
numbers.Add(20);
numbers.Add(30);
```

Now the logical contents are exactly:

```
Index:  0   1   2
Value: 10  20  30

Count = 3
Capacity = 1000
```

The remaining storage is reserved for future additions, not part of the collection's sequence.

This gives `List<T>` a useful invariant: its elements occupy a contiguous range of valid indexes from `0` through `Count - 1`.

If you need to populate arbitrary indexes in a preallocated structure, an array is a more natural choice. Or you can use a list and explicitly add placeholder elements first.

> What about InsertAt(index)? It must not have such a restriction, or does it?

`List<T>` has `Insert(index, item)`, rather than a method named `InsertAt()`.

It allows insertion at any index from `0` through `Count`, inclusive. It does not allow insertion at any index within `Capacity`.

C#

```
List<int> numbers = new List<int>(1000);

numbers.Insert(0, 10); // Valid
numbers.Insert(1, 20); // Valid
numbers.Insert(2, 30); // Valid

numbers.Insert(3, 40); // Valid: inserts at the end
numbers.Insert(500, 50); // Throws ArgumentOutOfRangeException
```

Why is index `3` valid when `Count` is 3? Because inserting at `Count` means appending to the end.

For insertion in the middle, existing elements must shift to make room:

C#

```
List<int> numbers = [10, 20, 30];

numbers.Insert(1, 15);

// Result: 10, 15, 20, 30
```

This takes O(n) time in the general case because elements may need to shift.

If the list has enough capacity, insertion doesn't require reallocating the internal array. But it may still require shifting elements.

> `EnsureCapacity(100)` vs `Capacity = 100`

Both can increase a list's internal storage, but their intent and behavior differ.

C#

```
List<int> numbers = new List<int>();

numbers.EnsureCapacity(100);
```

This means: ensure that capacity is at least 100.

The runtime may choose a larger capacity based on its growth strategy. It does not shrink capacity if the current capacity is already greater than 100.

Now consider:

C#

```
numbers.Capacity = 100;
```

This explicitly sets the capacity to 100.

* If the current capacity is smaller, the internal array is resized to the requested capacity.

* If the current capacity is larger, it shrinks the internal array to 100, provided `Count` is no greater than 100.

* If the requested capacity is below `Count`, an exception is thrown.

For example:

C#

```
List<int> numbers = new List<int>(200);

numbers.EnsureCapacity(100);
Console.WriteLine(numbers.Capacity); // 200

numbers.Capacity = 100;
Console.WriteLine(numbers.Capacity); // 100
```

So the practical distinction is:

| `EnsureCapacity()`                 | `Capacity` setter                          |
| ---------------------------------- | ------------------------------------------ |
| Guarantees a minimum capacity      | Sets a specific capacity                   |
| Doesn't shrink                     | Can shrink or grow                         |
| May allocate more than requested   | Sets the requested capacity                |
| Useful before adding many elements | Useful when explicitly controlling storage |

One more detail: `EnsureCapacity()` returns the resulting capacity, which can be useful if you want to inspect the actual capacity chosen.

> If capacity is 5 and you add a sixth element, does it grow to 10 or 8?

In the current .NET implementation, it grows to 10 under these conditions.

C#

```
List<int> numbers = new List<int>(5);

for (int i = 1; i <= 5; i++)
{
    numbers.Add(i);
}

Console.WriteLine(numbers.Count);    // 5
Console.WriteLine(numbers.Capacity); // 5

numbers.Add(6);

Console.WriteLine(numbers.Count);    // 6
Console.WriteLine(numbers.Capacity); // 10
```

The usual growth calculation doubles the current capacity:

```
Current capacity = 5
Minimum required = 6
New capacity = 5 * 2 = 10
```

If the doubled capacity were still insufficient for the requested minimum, the implementation would choose at least the required minimum instead.

The important point is that the growth factor is an implementation detail. The documented behavior guarantees enough capacity for the elements, not a particular growth factor. For interview purposes, understand the current doubling behavior, but describe the API guarantee as automatic growth when capacity is insufficient.

Your intuition is right: reserved capacity exists to reduce reallocations. The reason indexing and insertion are restricted by `Count` is that `List<T>` models a sequence of existing elements, not merely a block of allocated memory.
