# 2.5 `Queue<T>`

A `Queue<T>` represents a **FIFO** collection:

> **First In, First Out**

The item added first is the item removed first.

```csharp
var queue = new Queue<string>();

queue.Enqueue("Alice");
queue.Enqueue("Bob");
queue.Enqueue("Charlie");
```

The queue is:

```text
Alice → Bob → Charlie
```

If we remove an item:

```csharp
var person = queue.Dequeue();

Console.WriteLine(person); // Alice
```

Now:

```text
Bob → Charlie
```

## 1. Creating a Queue

```csharp
Queue<int> numbers = new Queue<int>();
```

Or:

```csharp
var numbers = new Queue<int>();
```

You can also initialize it with values:

```csharp
var numbers = new Queue<int>
{
    10,
    20,
    30
};
```

## 2. `Enqueue()`

Adds an item to the **end** of the queue.

```csharp
var queue = new Queue<string>();

queue.Enqueue("Alice");
queue.Enqueue("Bob");
queue.Enqueue("Charlie");
```

Result:

```text
Front
  ↓
Alice → Bob → Charlie
                    ↑
                   Back
```

`Enqueue()` is normally **O(1)**.

## 3. `Dequeue()`

Removes and returns the item at the **front**.

```csharp
string person = queue.Dequeue();
```

If the queue contains:

```text
Alice → Bob → Charlie
```

then:

```csharp
person
```

contains `"Alice"`.

The queue becomes:

```text
Bob → Charlie
```

`Dequeue()` is normally **O(1)**.

### Important

Calling `Dequeue()` on an empty queue throws:

```csharp
InvalidOperationException
```

So if you're not sure whether the queue contains an item, use `TryDequeue()`.

## 4. `TryDequeue()`

```csharp
if (queue.TryDequeue(out string? person))
{
    Console.WriteLine(person);
}
```

If the queue is empty, it returns `false` instead of throwing.

This is often preferable when an empty queue is an expected possibility.

## 5. `Peek()`

`Peek()` looks at the first item **without removing it**.

```csharp
var first = queue.Peek();
```

For:

```text
Alice → Bob → Charlie
```

`Peek()` returns:

```text
Alice
```

but the queue remains:

```text
Alice → Bob → Charlie
```

Like `Dequeue()`, `Peek()` throws `InvalidOperationException` if the queue is empty.

## 6. `TryPeek()`

The safe version is:

```csharp
if (queue.TryPeek(out string? person))
{
    Console.WriteLine(person);
}
```

It returns `false` when the queue is empty.

## 7. `Count`

You can check how many elements are currently in the queue:

```csharp
Console.WriteLine(queue.Count);
```

`Count` is **O(1)**.

Don't do this:

```csharp
queue.Count() // LINQ
```

when you already have:

```csharp
queue.Count
```

The property directly gives you the collection's count.

## 8. Checking whether an item exists

```csharp
bool exists = queue.Contains("Alice");
```

This requires searching through the queue, so it is **O(n)**.

A `Queue<T>` is designed for processing elements in order, not for fast arbitrary lookups.

## 9. `Clear()`

Removes all elements:

```csharp
queue.Clear();
```

After this:

```csharp
queue.Count == 0
```

## 10. Interfaces implemented by `Queue<T>`

This is important for our collections curriculum.

`Queue<T>` implements:

```text
IEnumerable<T>
IEnumerable
IReadOnlyCollection<T>
ICollection
ICollection<T>
```

The most useful one to remember conceptually is:

```text
Queue<T>
    └── ICollection<T>
          └── IEnumerable<T>
                └── IEnumerable
```

It also implements the non-generic `ICollection`.

This means you can treat a queue through an interface when appropriate:

```csharp
IEnumerable<string> people = queue;
```

or:

```csharp
ICollection<string> people = queue;
```

But those interfaces don't expose queue-specific operations such as `Dequeue()`.

That's an important distinction:

```csharp
Queue<string> queue = ...;

queue.Dequeue(); // available
```

versus:

```csharp
ICollection<string> collection = queue;

collection.Dequeue(); // doesn't exist
```

The interface determines what operations are exposed.

## 11. How `Queue<T>` is implemented

`Queue<T>` is implemented using an **array-based circular buffer**.

Conceptually:

```text
[ A ][ B ][ C ][   ][   ][   ]
  ↑           ↑
front        back
```

When elements are removed from the front, the queue doesn't physically shift every remaining element.

Instead, it keeps track of positions and wraps around the underlying array.

That's why removing from the front can remain **O(1)**.

When the internal array becomes full, the queue needs to allocate a larger array and copy the elements.

That resizing operation is **O(n)**.

However, individual `Enqueue()` operations are **amortized O(1)**.

## 12. Complexity

| Operation | Complexity |
|---|---:|
| `Enqueue()` | O(1) amortized |
| `Dequeue()` | O(1) |
| `TryDequeue()` | O(1) |
| `Peek()` | O(1) |
| `TryPeek()` | O(1) |
| `Count` | O(1) |
| `Contains()` | O(n) |
| `Clear()` | O(n) |

The important interview distinction is:

> `Enqueue()` is amortized O(1), because occasional resizing can require O(n) work.

## 13. Practical example

A queue is useful when work should be processed in the order it arrives.

For example, a simple job processor:

```csharp
var jobs = new Queue<string>();

jobs.Enqueue("Generate report");
jobs.Enqueue("Send email");
jobs.Enqueue("Process payment");

while (jobs.Count > 0)
{
    var job = jobs.Dequeue();

    Console.WriteLine($"Processing: {job}");
}
```

Output:

```text
Processing: Generate report
Processing: Send email
Processing: Process payment
```

This is the core idea behind FIFO processing.

## 14. `Queue<T>` vs `Stack<T>`

This is a very common interview comparison.

| `Queue<T>` | `Stack<T>` |
|---|---|
| FIFO | LIFO |
| First in, first out | Last in, first out |
| `Enqueue()` | `Push()` |
| `Dequeue()` | `Pop()` |
| `Peek()` | `Peek()` |

Think:

```text
Queue:  A → B → C
        ↑
      first out
```

versus:

```text
Stack:

    C  ← first out
    B
    A
```

## Interview questions

### Why is `Queue<T>.Dequeue()` O(1)?

Because `Queue<T>` uses an array-based circular buffer and maintains an index pointing to the front. It doesn't need to shift all remaining elements when removing the first item.

### Why is `Enqueue()` amortized O(1)?

Most insertions simply place the item into the next available position. Occasionally the internal array needs to grow, which requires copying elements and costs O(n). Across many insertions, the average cost is O(1).

### When would you use `Queue<T>`?

When items should be processed in the same order they were added—for example, job processing, request processing, or breadth-first traversal.

### `Queue<T>` or `List<T>` for FIFO processing?

`Queue<T>` communicates the intent directly and provides efficient FIFO operations. Using a `List<T>` and repeatedly removing the first element can require shifting elements and therefore be inefficient.

## What you should remember

If you're asked about `Queue<T>` in an interview, the core answer is:

> `Queue<T>` is a generic FIFO collection. You add items with `Enqueue()`, remove them with `Dequeue()`, and inspect the next item with `Peek()`. It is implemented using an array-based circular buffer, so enqueue and dequeue are generally O(1), with enqueue being amortized O(1) because of occasional resizing. It implements interfaces including `ICollection<T>`, `IReadOnlyCollection<T>`, and `IEnumerable<T>`.

## Follow-ups

> Can Queue be supplied with a Capacity parameter?

Yes. You can specify the initial capacity when creating a `Queue<T>`.

```
Queue<int> queue = new Queue<int>(capacity: 100);
```

This creates a queue with an initial capacity of at least 100 elements.

A few important points:

- Capacity: The amount of internal storage allocated.
- Count: The number of elements currently in the queue.
- Capacity does not limit the queue: If you enqueue more than 100 elements, the queue automatically grows.
- Performance: Specifying an appropriate initial capacity can reduce resizing and copying when you know approximately how many elements you'll add.

You can also specify capacity later using `EnsureCapacity()`:

```
queue.EnsureCapacity(200);
```

This ensures the internal capacity is at least 200 without changing the number of elements.

Interview takeaway: Like `List<T>`, `Queue<T>` separates `Count` from `Capacity`. Its capacity is a storage optimization, not a maximum size.
