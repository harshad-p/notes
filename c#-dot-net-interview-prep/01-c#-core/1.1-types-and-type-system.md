# 1.1 Types and Type System

This is one of the most important C# foundations because many later topics—collections, generics, boxing, memory, async code, EF Core, and performance—depend on understanding what a C# type actually means.

We'll go in this order:

1. Value types vs reference types
2. Stack vs heap — what this actually means in .NET
3. `struct` vs `class`
4. `record` vs `record class` vs `record struct`
5. Boxing and unboxing
6. Nullable value types
7. Nullable reference types

---

## 1.1.1 Value Types vs Reference Types

The first distinction to understand is **not simply where the object lives in memory**.

It is about **what a variable contains** and **how assignment and passing work**.

### Value type

A value-type variable directly represents its value.

Examples:

```csharp
int age = 37;
double price = 19.99;
bool active = true;
```

If you do:

```csharp
int a = 10;
int b = a;

b = 20;
```

`a` remains `10`.

Why?

Because assigning `a` to `b` copies the value.

Conceptually:

```text
a → 10

b = a

a → 10
b → 10

b = 20

a → 10
b → 20
```

The two variables are independent.

Common value types include:

- `int`
- `long`
- `double`
- `decimal`
- `bool`
- `char`
- `struct`
- `enum`

---

### Reference type

A reference-type variable contains a **reference to an object**.

For example:

```csharp
var person1 = new Person
{
    Name = "Harshad"
};

var person2 = person1;

person2.Name = "John";
```

Now:

```csharp
person1.Name
```

is also `"John"`.

Why?

Because `person1` and `person2` refer to the **same object**.

Conceptually:

```text
person1 ──┐
          ├──> Person object
person2 ──┘
```

The assignment:

```csharp
person2 = person1;
```

doesn't create another `Person`.

It copies the **reference**.

Common reference types include:

- `class`
- `record class`
- `string`
- arrays
- delegates
- interfaces
- most objects created with `new`

---

### The important distinction

A common interview answer is:

> “Value types are stored on the stack and reference types are stored on the heap.”

**Don't use that as your mental model.**

It is an oversimplification and can lead you to incorrect conclusions.

The important question is:

> **Does the variable contain the value itself, or a reference to an object?**

We'll get into the stack/heap distinction next.

---

## 1.1.2 Stack vs Heap — What This Actually Means in .NET

This is where many C# explanations become misleading.

You will often hear:

> Value types → stack  
> Reference types → heap

That's **not universally true**.

A better model is:

### The stack

A thread has a stack used for its method-call execution state.

When a method is called, the runtime needs space for things such as:

- method parameters
- local variables
- return information
- execution state

That storage is associated with the current call stack.

For example:

```csharp
void Calculate()
{
    int x = 10;
    int y = 20;

    int result = x + y;
}
```

The local variables can be represented in the method's stack frame.

But that does **not** mean every `int` in .NET lives on the stack.

---

### The heap

The managed heap is where the .NET GC manages objects.

For example:

```csharp
var person = new Person();
```

The `Person` object is normally allocated on the managed heap.

The variable `person` contains a reference to that object.

So you can conceptually think:

```text
Stack / local execution state

person ────────┐
               │
               ▼
        Managed heap
        ┌─────────────┐
        │ Person      │
        │ Name = ...  │
        └─────────────┘
```

But the exact physical representation is controlled by the runtime and JIT.

---

### A value type can exist on the heap

Consider:

```csharp
class Person
{
    public int Age;
}
```

When you create:

```csharp
var person = new Person();
```

the `Person` object is on the managed heap.

Its `Age` field is an `int`, a value type.

But that `int` is **inside the heap-allocated object**.

So here we have:

```text
Heap
┌───────────────────┐
│ Person object     │
│                   │
│ Age = 37          │  ← int value type
└───────────────────┘
```

The fact that `Age` is a value type doesn't magically move it to the stack.

---

### A value type can also be boxed

We'll cover boxing shortly, but:

```csharp
int x = 10;

object o = x;
```

The `int` gets wrapped in an object on the managed heap.

So again, a value type can participate in heap allocation.

---

### The better mental model

Don't ask:

> “Is this value type on the stack?”

Ask:

> **“Where is this value stored in this particular situation, and is an object allocation involved?”**

The runtime, JIT optimizations, escape analysis, struct placement, and object layout can affect the actual implementation.

For interviews, saying:

> “Value types are generally stored directly where the containing variable or object is stored, while reference types refer to objects managed on the heap”

is much safer than saying:

> “Value types live on the stack.”

---

## 1.1.3 `struct` vs `class`

A `struct` is a **value type**.

A `class` is a **reference type**.

For example:

```csharp
struct Point
{
    public int X;
    public int Y;
}

class Person
{
    public string Name;
}
```

Now:

```csharp
Point p1 = new Point { X = 10, Y = 20 };
Point p2 = p1;

p2.X = 100;
```

`p1.X` remains `10`.

That's because `p2 = p1` copies the entire value.

With a class:

```csharp
Person p1 = new Person { Name = "Harshad" };
Person p2 = p1;

p2.Name = "John";
```

Both variables refer to the same object.

---

### Structs are not simply "small classes"

This is important.

A `struct` has value semantics.

A class has reference semantics.

That difference affects:

- copying
- equality
- nullability
- boxing
- memory layout
- parameter passing
- mutation
- allocation behavior

---

### When does a struct make sense?

Structs are generally useful for **small values that conceptually represent one value**.

Examples:

```csharp
Point
DateTime
TimeSpan
Guid
decimal
```

A coordinate is a good example:

```csharp
public readonly struct Point
{
    public double X { get; }
    public double Y { get; }

    public Point(double x, double y)
    {
        X = x;
        Y = y;
    }
}
```

You can copy a `Point` without worrying that both variables now refer to the same mutable object.

---

### Why not make everything a struct?

Because structs are copied by value.

Imagine:

```csharp
LargeStruct a = ...;
LargeStruct b = a;
```

The entire value may need to be copied.

Large structs can therefore introduce copying costs.

Mutable structs can also be particularly confusing because changing one copy doesn't change another.

For example:

```csharp
Point p1 = ...;
Point p2 = p1;

p2.X = 100;
```

You're modifying `p2`, not `p1`.

So a common design guideline is:

> Use structs for small value-like concepts where value semantics make sense; use classes when you need reference semantics or the object has more substantial identity/state.

---

## 1.1.4 `record` vs `record class` vs `record struct`

Records are primarily about **data-oriented types and value-based equality**.

There are three relevant forms:

```csharp
record Person(string Name);
```

```csharp
record class Person(string Name);
```

```csharp
record struct Person(string Name);
```

The first two are reference types.

The third is a value type.

---

### `record` and `record class`

These are effectively the same kind of type:

```csharp
record Person(string Name);
```

is a reference-type record.

You can explicitly write:

```csharp
record class Person(string Name);
```

The key feature is that records provide **value-based equality semantics** by default.

For example:

```csharp
var p1 = new Person("Harshad");
var p2 = new Person("Harshad");

Console.WriteLine(p1 == p2);
```

For a record, this evaluates to `true`.

The objects are separate objects, but their relevant data is equal.

Compare that with a normal class:

```csharp
class Person
{
    public string Name { get; set; }
}
```

Two separately created `Person` objects are normally not equal unless you implement equality yourself.

---

### `record struct`

A `record struct` combines:

- struct/value-type semantics
- record/value-based equality

For example:

```csharp
record struct Point(int X, int Y);
```

Now:

```csharp
var p1 = new Point(10, 20);
var p2 = new Point(10, 20);

Console.WriteLine(p1 == p2);
```

is `true`.

And because it is a struct:

```csharp
var p2 = p1;
```

copies the value.

---

### The useful comparison

| Type | Value/reference | Equality by default | Typical use |
|---|---|---|---|
| `class` | Reference | Reference identity | Objects with identity/state |
| `record class` | Reference | Value-based | Data-oriented reference objects |
| `struct` | Value | Value semantics | Small value-like types |
| `record struct` | Value | Value-based | Small data/value objects |

One important nuance: `record struct` can be mutable by default, whereas `readonly record struct` can be used when you want immutable value semantics.

---

## 1.1.5 Boxing and Unboxing

Boxing happens when a **value type is converted to a reference type**, usually `object` or an interface.

Example:

```csharp
int number = 42;

object value = number;
```

What's happening?

The integer value needs to be represented as an object.

Conceptually:

```text
int number
    │
    │ boxing
    ▼
object containing 42
```

The runtime creates an object representation containing the value.

That can involve a heap allocation.

---

### Unboxing

Going back from the boxed object to the value type:

```csharp
object value = 42;

int number = (int)value;
```

That's unboxing.

The runtime checks that the boxed value is actually an `int` and extracts the value.

This will fail:

```csharp
object value = 42;

long number = (long)value;
```

Even though an `int` can normally be numerically converted to `long`.

Why?

Because the boxed object contains an **`int`**, not a boxed `long`.

You would need:

```csharp
long number = (int)value;
```

That first unboxes the `int`, then converts it to `long`.

---

### Why should you care about boxing?

Because boxing can introduce:

- allocations
- copying
- additional runtime work
- GC pressure

This matters particularly in performance-sensitive code or inside large loops.

Generics often help avoid boxing.

For example, a generic method:

```csharp
void Process<T>(T value)
{
}
```

can operate on a value type without necessarily boxing it merely because it is being passed to the generic method.

---

## 1.1.6 Nullable Value Types

Normally, a value type cannot be `null`.

This doesn't work:

```csharp
int age = null;
```

because `int` must contain an integer value.

But sometimes you genuinely need:

> “There is no value.”

For example:

```csharp
int? age = null;
```

`int?` is shorthand for:

```csharp
Nullable<int>
```

Now the variable can represent either:

- an `int`
- no value

For example:

```csharp
int? age = 37;

age = null;
```

---

### Why is this useful?

Consider a database column:

```text
MiddleName
---------
Harshad
null
John
null
```

Or:

```text
DateOfBirth
-----------
1990-01-01
null
1985-05-12
```

`null` has a meaningful distinction from:

```text
DateOfBirth = 0001-01-01
```

The latter is an actual `DateTime` value.

Nullable value types allow you to represent **absence of a value** without inventing a special value.

---

### Checking a nullable value

You can write:

```csharp
int? age = 37;

if (age.HasValue)
{
    Console.WriteLine(age.Value);
}
```

Or more naturally:

```csharp
if (age is int actualAge)
{
    Console.WriteLine(actualAge);
}
```

You can also use the null-coalescing operator:

```csharp
int actualAge = age ?? 0;
```

Meaning:

> Use `age` if it has a value; otherwise use `0`.

---

## 1.1.7 Nullable Reference Types

This is a different concept.

Reference types have historically been able to contain `null`:

```csharp
string name = null;
```

The compiler couldn't reliably tell you whether that was intentional.

That could eventually cause:

```csharp
name.Length
```

to throw:

```text
NullReferenceException
```

Nullable Reference Types were introduced to let the **compiler help detect this class of problem**.

You can write:

```csharp
string name = "Harshad";
```

which communicates:

> `name` is expected to contain a non-null string.

And:

```csharp
string? name = null;
```

which communicates:

> `name` is allowed to be null.

---

### Important: `string?` does not create a different runtime type

This is an important distinction from:

```csharp
int?
```

`int?` is actually `Nullable<int>`.

But:

```csharp
string?
```

is **not a different runtime type from `string`**.

The `?` on a reference type primarily provides **nullability information to the compiler and tooling**.

For example:

```csharp
string? name = GetName();

Console.WriteLine(name.Length);
```

The compiler warns because `name` might be null.

You can establish that it isn't null:

```csharp
if (name != null)
{
    Console.WriteLine(name.Length);
}
```

or use the null-conditional operator:

```csharp
Console.WriteLine(name?.Length);
```

---

## The Important Distinction: `int?` vs `string?`

This is worth remembering because interviewers sometimes test it.

### Nullable value type

```csharp
int?
```

is:

```csharp
Nullable<int>
```

It is a wrapper that can represent:

> an `int` value OR no value.

### Nullable reference type

```csharp
string?
```

is:

> a compiler annotation saying the reference is allowed to be null.

The runtime still sees a `System.String` reference.

---

## Putting Everything Together

Here's a useful way to connect the concepts:

| Concept | Core idea |
|---|---|
| Value type | Variable represents/carries the value |
| Reference type | Variable contains a reference to an object |
| Stack | Thread-associated execution storage; don't equate it with "value types" |
| Managed heap | GC-managed object storage |
| `struct` | User-defined value type |
| `class` | User-defined reference type |
| `record class` | Reference type with record/value-based equality semantics |
| `record struct` | Value type with record/value-based equality semantics |
| Boxing | Value type represented as an object/reference |
| Unboxing | Extracting the value from a boxed value |
| `int?` | `Nullable<int>` |
| `string?` | Compiler nullability annotation |

### The mental model I want you to have

Don't memorize:

> **struct = stack, class = heap**

Instead:

> **`struct` and `class` determine value vs reference semantics. Where the actual data is stored is a separate runtime/memory-layout question.**

And don't memorize:

> **`?` means nullable.**

Instead distinguish:

> **`int?` changes the type to `Nullable<int>`, while `string?` gives the compiler information that the reference may be null.**

Those distinctions will make several later topics—**generics, equality, GC, allocations, EF Core, async, and performance**—much easier to understand.

## Follow-ups

> Are record and record the same thing?

Yes. **`record` by itself means `record class`**.

So these are equivalent:

```csharp
record Person(string Name);
```

```csharp
record class Person(string Name);
```

Both create a **reference type** with record semantics.

The explicit `record class` form is mainly useful when you want to make the distinction obvious, especially when comparing it with `record struct`.

---

### `record struct` in detail

A `record struct` combines two ideas:

1. **Struct semantics** → it is a value type.
2. **Record semantics** → equality is based on its data rather than object identity.

For example:

```csharp
public record struct Point(int X, int Y);
```

Then:

```csharp
var p1 = new Point(10, 20);
var p2 = new Point(10, 20);

Console.WriteLine(p1 == p2); // true
```

Why?

Because `p1` and `p2` contain the same values.

They're still two independent value instances.

If you do:

```csharp
var p2 = p1;

p2.X = 100;
```

then:

```text
p1.X == 10
p2.X == 100
```

because assigning a struct copies the value.

---

### Compare that with a record class

```csharp
public record Point(int X, int Y);
```

Now:

```csharp
var p1 = new Point(10, 20);
var p2 = p1;
```

`p1` and `p2` refer to the **same object**.

So the fundamental difference is still:

```text
record
       → reference type

record struct
       → value type
```

Record semantics don't change that.

#### What does `record` add?

A normal struct already has value semantics.

So why would you want a `record struct`?

Because records provide convenient **data-oriented equality and generated functionality**.

For example:

```csharp
public record struct Money(decimal Amount, string Currency);
```

You get useful value-based behavior:

```csharp
var a = new Money(100, "EUR");
var b = new Money(100, "EUR");

Console.WriteLine(a == b); // true
```

This is exactly what you usually want for a value such as:

> 100 EUR

The identity of the object doesn't matter. Its **data** matters.

---

### Without records, does a `struct` need its own `Equals()` implementation?

**No — not necessarily.**

A normal struct already has **value-based equality semantics by default**.

For example:

```csharp
public struct Point
{
    public int X;
    public int Y;
}
```

You can do:

```csharp
var p1 = new Point { X = 10, Y = 20 };
var p2 = new Point { X = 10, Y = 20 };

Console.WriteLine(p1.Equals(p2)); // true
```

You don't have to implement `Equals()` yourself.

The default `ValueType.Equals()` implementation compares the fields of the struct.

However, you **can override `Equals()`** when you want to define your own equality semantics.

For example, suppose you have:

```csharp
public struct Money
{
    public decimal Amount;
    public string Currency;
}
```

You might decide that equality should be based on some specific business rule, in which case you can implement `IEquatable<Money>` and override `Equals()`.

```csharp
public readonly struct Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    public bool Equals(Money other) =>
        Amount == other.Amount &&
        Currency == other.Currency;

    public override bool Equals(object? obj) =>
        obj is Money other && Equals(other);

    public override int GetHashCode() =>
        HashCode.Combine(Amount, Currency);
}
```

The important distinction is:

> **A struct already has value semantics. A record gives you more convenient, compiler-generated value-oriented behavior.**

And for performance-sensitive structs, implementing `IEquatable<T>` yourself can avoid some costs associated with the general `ValueType.Equals()` path.

---

### So if a struct already provides value semantics comparison, why have record struct?

Exactly — this is the subtle part. **`record struct` wasn't introduced simply to give structs value equality.** Regular structs already have that.

The reason to use a `record struct` is that it gives you a **more convenient, explicit data-oriented type with compiler-generated record features**.

#### Start with a normal struct

```csharp
public struct Point
{
    public int X { get; set; }
    public int Y { get; set; }
}
```

You already get value semantics:

```csharp
var p1 = new Point { X = 10, Y = 20 };
var p2 = new Point { X = 10, Y = 20 };

Console.WriteLine(p1.Equals(p2)); // true
```

But if you want a good-quality value type, you may end up writing quite a bit yourself:

```csharp
public struct Point : IEquatable<Point>
{
    public int X { get; }
    public int Y { get; }

    public bool Equals(Point other) =>
        X == other.X && Y == other.Y;

    public override bool Equals(object? obj) =>
        obj is Point other && Equals(other);

    public override int GetHashCode() =>
        HashCode.Combine(X, Y);

    public static bool operator ==(Point left, Point right) =>
        left.Equals(right);

    public static bool operator !=(Point left, Point right) =>
        !left.Equals(right);
}
```

And you may want:

- concise construction
- `ToString()` based on the data
- `with` expressions
- generated equality members
- deconstruction
- a clear declaration that this type is **data/value-oriented**

That's where `record struct` helps.

#### The same thing as a record struct

```csharp
public record struct Point(int X, int Y);
```

That's a very compact declaration.

The compiler generates the record-oriented behavior for you.

You can then do:

```csharp
var p1 = new Point(10, 20);
var p2 = new Point(10, 20);

Console.WriteLine(p1 == p2); // true
```

And:

```csharp
var p3 = p1 with { X = 50 };
```

You also get a useful generated representation:

```csharp
Console.WriteLine(p1);
```

which represents the record's data rather than the default struct type-name representation.

---

### So what's the real difference?

Think of it this way:

#### `struct`

Says:

> **“This is a value type.”**

You get value semantics, but you're responsible for deciding how much additional behavior you want to implement.

#### `record struct`

Says:

> **“This is a value type whose identity is entirely its data, and I want the compiler to generate the record-style data behavior for me.”**

That's a stronger **design signal**.

#### An example where it becomes clearer

Suppose you're representing a coordinate.

With a normal struct:

```csharp
public struct Coordinate
{
    public double Latitude { get; }
    public double Longitude { get; }

    public Coordinate(double latitude, double longitude)
    {
        Latitude = latitude;
        Longitude = longitude;
    }

    // Equality implementation...
    // GetHashCode...
    // etc.
}
```

With a record struct:

```csharp
public readonly record struct Coordinate(
    double Latitude,
    double Longitude);
```

That declaration tells another developer almost everything they need to know:

> This is a small value type, its identity is its data, and it should be immutable.

That's the real benefit.

#### One correction to something I said earlier

I said:

> “A normal struct already has value-based equality.”

That's correct, but there's an important nuance.

The **default equality implementation** for a struct is value-based, but it's not necessarily the equality implementation you'd want for every custom value type, and it isn't equivalent to all the generated behavior of a record.

For example, a record struct gives you strongly typed equality support and generated members such as `==`, `!=`, `GetHashCode()`, `ToString()`, and deconstruction based on its declared data.

So don't think:

> `struct` = equality, `record struct` = equality plus nothing.

Think:

> **`struct` gives me value-type semantics.**  
> **`record struct` gives me value-type semantics + convenient record/data semantics.**

And `readonly record struct` adds:

> **immutable value-type semantics.**

That's why all three exist.

---

### So you mean to say that for structs p1 == p2 will return false? But p1.Equals(p2) will return true? And records gives you the ability where p1 == p2 returns true?

Yes — **with one important qualification**. Your understanding is basically correct.

For a **normal struct**, these two are different:

```csharp
public struct Point
{
    public int X;
    public int Y;
}
```

Then:

```csharp
var p1 = new Point { X = 10, Y = 20 };
var p2 = new Point { X = 10, Y = 20 };
```

#### `p1.Equals(p2)`

```csharp
p1.Equals(p2)
```

returns **`true`** by default, because structs have value-based equality.

#### `p1 == p2`

```csharp
p1 == p2
```

**does not automatically work for a normal struct.**

You generally need to define the `==` operator yourself.

So this:

```csharp
Console.WriteLine(p1 == p2);
```

will result in a **compile-time error**, not `false`.

That's the important correction.

---

#### `record struct`

With:

```csharp
public record struct Point(int X, int Y);
```

you get generated equality operators.

So:

```csharp
var p1 = new Point(10, 20);
var p2 = new Point(10, 20);

Console.WriteLine(p1 == p2);
```

returns:

```text
true
```

So the comparison looks like this:

| | Normal `struct` | `record struct` |
|---|---|---|
| Value type | Yes | Yes |
| `Equals()` value comparison | Yes, by default | Yes |
| `==` generated for value comparison | **No** | **Yes** |
| `!=` generated | **No** | **Yes** |
| Record-style generated members | No | Yes |
| `with` expression | No | Yes |

#### So the key distinction is:

```text
struct
    → value semantics
    → Equals() compares values
    → == is NOT automatically defined

record struct
    → value semantics
    → Equals() compares values
    → == is generated to compare values
    → additional record features
```

And that's actually a **very good reason** for `record struct`: you can express a small value object concisely without manually implementing all that boilerplate.

One small caveat: you *can* define `==` yourself on a normal struct. It's just not supplied automatically by the language.

---

#### `record struct` is mutable by default

This is an important detail.

Consider:

```csharp
public record struct Point(int X, int Y);
```

You can do:

```csharp
var point = new Point(10, 20);

point.X = 50;
```

The properties are settable.

So the record struct is **not automatically immutable**.

That's where `readonly record struct` comes in.

---

### `readonly record struct`

You can declare:

```csharp
public readonly record struct Point(int X, int Y);
```

Now the struct is intended to be **immutable**.

You can't do:

```csharp
point.X = 50;
```

after creation.

Instead:

```csharp
var point = new Point(10, 20);
```

remains:

```text
X = 10
Y = 20
```

You create another value when you need a different state:

```csharp
var newPoint = point with { X = 50 };
```

Now:

```text
point    → (10, 20)
newPoint → (50, 20)
```

The original value hasn't changed.

---

### Why is `readonly` useful for structs?

This gets into an important C# performance/detail issue.

Structs are values and can be copied.

If a struct is mutable, the compiler/runtime sometimes has to be careful about whether you're modifying:

- the original struct
- a copy of the struct
- a temporary value

Readonly structs make the intent clearer:

> **Once this value exists, its state doesn't change.**

They are particularly appropriate for things that conceptually represent immutable values:

```text
Point
Money
Temperature
Coordinates
Distance
Color
```

For example:

```csharp
public readonly record struct Money(
    decimal Amount,
    string Currency);
```

Then:

```csharp
var price = new Money(100, "EUR");
```

The `price` represents one immutable value.

If you need another value:

```csharp
var discounted = price with { Amount = 80 };
```

---

### `record struct` vs `readonly record struct`

The simplest distinction is:

| | `record struct` | `readonly record struct` |
|---|---|---|
| Value type | Yes | Yes |
| Record/value equality | Yes | Yes |
| Can mutate properties | Yes | No |
| Intended to be immutable | No | Yes |
| `with` expressions | Yes | Yes |
| Good for value objects | Yes | **Often preferable** |

---

### One subtle point about `with`

You may have seen:

```csharp
var updated = person with
{
    Name = "John"
};
```

Records make this pattern convenient.

It works with record structs too.

For example:

```csharp
public readonly record struct Point(int X, int Y);

var p1 = new Point(10, 20);

var p2 = p1 with
{
    X = 50
};
```

You now have:

```text
p1 = (10, 20)
p2 = (50, 20)
```

This is useful when you want immutable, value-oriented data but still want an easy way to create a modified version.

---

### One more important distinction: `readonly struct` vs `readonly record struct`

These are **not the same thing**.

You can have:

```csharp
readonly struct Point
{
    public int X { get; }
    public int Y { get; }

    public Point(int x, int y)
    {
        X = x;
        Y = y;
    }
}
```

That's a normal readonly struct.

Or:

```csharp
readonly record struct Point(int X, int Y);
```

That's a **record struct**, so you additionally get record-oriented generated behavior such as value-based equality, useful generated members, and `with` support.

Think of it as:

```text
readonly struct
    = value type + readonly

readonly record struct
    = value type
    + readonly
    + record semantics
```

---

### How I would choose between them

Suppose you're representing money:

```csharp
public readonly record struct Money(
    decimal Amount,
    string Currency);
```

This is a good fit because:

- it is a small value
- identity doesn't matter
- equality should be based on its contents
- you don't want it changing after creation

For a larger domain object such as:

```csharp
public record Customer(
    int Id,
    string Name);
```

a `record`/`record class` is generally more natural because the object is reference-based and potentially represents a domain entity or larger data structure.

And for a normal mutable object with identity:

```csharp
public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; }
}
```

a class is appropriate.

---

### Can I have a `readonly class` like a `readonly struct`?

**No. C# doesn't have a `readonly class` declaration.**

You can write:

```csharp
public readonly struct Point
{
}
```

but not:

```csharp
public readonly class Person
{
}
```

The reason is that `readonly` has a particular meaning for **value types**: it tells the compiler that the struct's instance state cannot be modified after construction.

For classes, you achieve immutability through the **members of the class**, rather than marking the entire class `readonly`.

For example:

```csharp
public class Person
{
    public string Name { get; }

    public Person(string name)
    {
        Name = name;
    }
}
```

Now:

```csharp
var person = new Person("Harshad");
```

There is no setter through which `Name` can be changed.

You can also use an `init` accessor:

```csharp
public class Person
{
    public string Name { get; init; }
}
```

Then:

```csharp
var person = new Person
{
    Name = "Harshad"
};
```

but this won't compile:

```csharp
person.Name = "John";
```

after initialization.

#### One important distinction

Even with:

```csharp
public class Person
{
    public string Name { get; }
}
```

the **reference itself** can still be changed:

```csharp
Person person1 = new("Harshad");
Person person2 = new("John");

person1 = person2;
```

What is immutable is the **state of the `Person` object through its public API**, not the variable holding the reference.

So:

> **`readonly struct` = language-level readonly guarantee for the struct's fields.**

Whereas:

> **Immutable class = a design where the object's state cannot be changed after construction.**

That's an important distinction you'll encounter again when we get to **immutability, concurrency, and thread safety**.

---

### The mental model

Think of the four forms like this:

```text
class
    Reference semantics
    Identity-based equality by default

record / record class
    Reference semantics
    Value-based equality

struct
    Value semantics
    Value-based equality

record struct
    Value semantics
    Record-style value equality

readonly record struct
    Value semantics
    Record-style value equality
    Immutable
```

The key thing is that **`record` does not mean immutable**, and **`struct` does not mean immutable**.

`readonly record struct` is the combination where you explicitly get a **readonly value type with record semantics**.
