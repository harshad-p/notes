# 1.3 Object-Oriented Programming

Object-oriented programming (OOP) is a way of organizing software around objects that combine state and behavior.

The four commonly named OOP principles are encapsulation, inheritance, polymorphism, and abstraction. Let's understand what each actually solves, then look at how they work together.

## 1. Encapsulation

Encapsulation means controlling access to an object's internal state and exposing operations through which other code can interact with it.

Consider a bank account:

C#

```
public class BankAccount
{
    public decimal Balance { get; private set; }

    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentException("Amount must be positive.");

        Balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentException("Amount must be positive.");

        if (amount > Balance)
            throw new InvalidOperationException("Insufficient funds.");

        Balance -= amount;
    }
}
```

External code can do this:

C#

```
var account = new BankAccount();

account.Deposit(500);
account.Withdraw(100);

Console.WriteLine(account.Balance); // 400
```

But it cannot do this:

C#

```
account.Balance = -1000; // Compile-time error
```

The class controls how its balance changes, so it can protect its invariants.

Notice that encapsulation is more than making fields private. It is about protecting the rules governing an object's state.

For example, this is technically encapsulated but doesn't enforce much:

C#

```
public class BankAccount
{
    private decimal _balance;

    public decimal GetBalance() => _balance;

    public void SetBalance(decimal value) => _balance = value;
}
```

The field is private, but callers can still assign any balance through `SetBalance`. The implementation hides the field without protecting the underlying rule.

When useful: business entities, domain objects, configuration with validation, and any object whose state must remain consistent.

## 2. Inheritance

Inheritance allows a class to derive from another class, inheriting its accessible members and potentially extending or changing its behavior.

For example:

C#

```
public class Animal
{
    public string Name { get; set; }

    public void Eat()
    {
        Console.WriteLine($"{Name} is eating.");
    }
}

public class Dog : Animal
{
    public void Fetch()
    {
        Console.WriteLine($"{Name} is fetching.");
    }
}
```

Now:

C#

```
var dog = new Dog { Name = "Buddy" };

dog.Eat();    // Inherited
dog.Fetch();  // Defined in Dog
```

`Dog` inherits `Name` and `Eat()` from `Animal`.

The relationship is often described as an is-a relationship: a dog is an animal.

However, inheritance isn't just a way to avoid repeating code. It creates a relationship between types and can constrain how derived classes behave.

For example, if many parts of your application depend on `Animal`, a derived class should behave in ways those parts reasonably expect from an animal.

That leads to the idea of substitutability, which is related to the Liskov Substitution Principle.

When useful: when types have a genuine conceptual relationship and derived types can honor the behavior expected of the base type.

Trade-off: inheritance introduces coupling. Changes in a base class can affect derived classes, and deep inheritance hierarchies can become difficult to reason about.

## 3. Polymorphism

Polymorphism allows code to work with a common type or contract while the actual object determines which implementation runs.

There are different forms of polymorphism in C#. The most relevant here is runtime polymorphism through virtual methods and interfaces.

Consider:

C#

```
public class Animal
{
    public virtual void Speak()
    {
        Console.WriteLine("Some sound");
    }
}

public class Dog : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Woof");
    }
}

public class Cat : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Meow");
    }
}
```

Now:

C#

```
Animal animal1 = new Dog();
Animal animal2 = new Cat();

animal1.Speak(); // Woof
animal2.Speak(); // Meow
```

Both variables are declared as `Animal`, but the actual objects are `Dog` and `Cat`.

When `Speak()` is called, C# dispatches the call to the implementation corresponding to the actual runtime type.

This is runtime polymorphism.

The benefit becomes clearer when you have a collection:

C#

```
List<Animal> animals =
[
    new Dog(),
    new Cat()
];

foreach (Animal animal in animals)
{
    animal.Speak();
}
```

The calling code doesn't need to check whether each object is a dog or cat.

Without polymorphism, you might end up with code like:

C#

```
if (animal is Dog)
{
    // Dog behavior
}
else if (animal is Cat)
{
    // Cat behavior
}
```

As more types are introduced, such conditional logic can spread throughout the application.

Polymorphism lets the behavior live with the relevant implementations.

### Compile-time polymorphism

C# also supports forms of polymorphism resolved at compile time, such as method overloading:

C#

```
public void Print(int value) { }

public void Print(string value) { }
```

The compiler chooses the appropriate overload based on the argument types and overload-resolution rules.

The key distinction:

* Compile-time polymorphism: the compiler selects an applicable implementation based on types and overload rules.

* Runtime polymorphism: virtual dispatch or interface dispatch selects behavior based on the runtime object.

## 4. Abstraction

Abstraction means exposing the essential capabilities of something while hiding unnecessary implementation details.

Imagine an application that sends notifications.

The application needs to send a message. It shouldn't necessarily need to know how SMTP, an SMS gateway, or a push notification provider works internally.

We can define a contract:

C#

```
public interface INotificationSender
{
    Task SendAsync(string recipient, string message);
}
```

Implementations can handle different delivery mechanisms:

C#

```
public class EmailSender : INotificationSender
{
    public Task SendAsync(string recipient, string message)
    {
        Console.WriteLine("Sending email...");
        return Task.CompletedTask;
    }
}

public class SmsSender : INotificationSender
{
    public Task SendAsync(string recipient, string message)
    {
        Console.WriteLine("Sending SMS...");
        return Task.CompletedTask;
    }
}
```

The application code depends on the abstraction:

C#

```
public class NotificationService
{
    private readonly INotificationSender _sender;

    public NotificationService(INotificationSender sender)
    {
        _sender = sender;
    }

    public Task NotifyAsync(string recipient, string message)
    {
        return _sender.SendAsync(recipient, message);
    }
}
```

`NotificationService` doesn't know which provider is being used. It knows only the operations offered by `INotificationSender`.

This reduces its dependency on implementation details.

Abstraction and encapsulation are related, but they aren't the same:

* Encapsulation controls access to internal state and implementation.

* Abstraction presents a simpler model or contract that hides irrelevant complexity.

For example, a class can encapsulate its private fields without offering a particularly useful abstraction. An interface can provide an abstraction without itself containing any implementation state.

## 5. Composition vs inheritance

This is a particularly useful design decision in real applications.

Inheritance models an is-a relationship. Composition models a has-a relationship or delegates work to another object.

Suppose you have a `Car` and need an engine.

### Inheritance approach

C#

```
public class Engine
{
    public void Start()
    {
        Console.WriteLine("Engine started.");
    }
}

public class Car : Engine
{
}
```

This says a car is an engine, which is conceptually incorrect.

It may technically compile, but the type relationship doesn't represent the domain.

### Composition approach

C#

```
public class Engine
{
    public void Start()
    {
        Console.WriteLine("Engine started.");
    }
}

public class Car
{
    private readonly Engine _engine;

    public Car(Engine engine)
    {
        _engine = engine;
    }

    public void Start()
    {
        _engine.Start();
    }
}
```

Now a car has an engine and delegates engine-related work to it.

This is composition.

The structural difference

Inheritance

Engine

Car

Car derives from Engine

Composition

Car

Engine

Car contains or uses an Engine

Composition also makes it easier to replace or vary behavior.

For example, a car could use different engine implementations:

C#

```
public interface IEngine
{
    void Start();
}

public class ElectricEngine : IEngine
{
    public void Start() => Console.WriteLine("Electric engine started.");
}

public class PetrolEngine : IEngine
{
    public void Start() => Console.WriteLine("Petrol engine started.");
}

public class Car
{
    private readonly IEngine _engine;

    public Car(IEngine engine)
    {
        _engine = engine;
    }

    public void Start() => _engine.Start();
}
```

Now the same `Car` class can work with either engine.

### Comparison

|Inheritance|Composition|
| --- | --- |
|Models an is-a relationship|Models a has-a/uses relationship|
|Reuses or specializes inherited behavior|Delegates behavior to collaborators|
|Tightly couples derived type to base type|Allows collaborators to be replaced|
|Useful for genuine type hierarchies|Useful for combining independent capabilities|

Composition is often preferred when you simply want to reuse behavior or make dependencies replaceable. Inheritance remains useful when the subtype relationship itself is meaningful.

## 6. `virtual`, `override`, and `new`

These keywords are closely related, but they do different things.

### `virtual` and `override`

`virtual` allows derived classes to replace a base implementation. `override` provides that replacement.

C#

```
public class Base
{
    public virtual void Show()
    {
        Console.WriteLine("Base");
    }
}

public class Derived : Base
{
    public override void Show()
    {
        Console.WriteLine("Derived");
    }
}
```

Consider:

C#

```
Base obj = new Derived();
obj.Show();
```

Output:

```
Derived
```

The method is selected through runtime dispatch.

### `new` hides a member

Now consider:

C#

```
public class Base
{
    public void Show()
    {
        Console.WriteLine("Base");
    }
}

public class Derived : Base
{
    public new void Show()
    {
        Console.WriteLine("Derived");
    }
}
```

Then:

C#

```
Derived derived = new Derived();
Base baseRef = derived;

derived.Show(); // Derived
baseRef.Show(); // Base
```

Why does the output differ?

Because `new` does not create a virtual override. It declares a separate member that hides the inherited one. Which member is called depends on the compile-time type of the expression.

### Comparison

|Keyword|Meaning|Dispatch|
| --- | --- | --- |
|`virtual`|Allows overriding|Runtime dispatch when called virtually|
|`override`|Replaces a virtual/abstract inherited member|Runtime dispatch|
|`new`|Hides an inherited member|Normally based on compile-time type|
|`sealed override`|Overrides but prevents further overrides|Runtime dispatch, no further override|

A common mistake is to use `new` when intending polymorphic behavior. It can lead to surprising results because code using a base-type reference can call a different implementation from code using the derived type.

## 7. Abstract classes vs interfaces

Both can define contracts that other types implement, but they serve different purposes.

### Abstract class

An abstract class can combine shared implementation, state, constructors, and abstract members that derived classes must implement.

C#

```
public abstract class PaymentProcessor
{
    protected string ProviderName { get; }

    protected PaymentProcessor(string providerName)
    {
        ProviderName = providerName;
    }

    public void LogStart()
    {
        Console.WriteLine($"Starting {ProviderName}");
    }

    public abstract Task ProcessAsync(decimal amount);
}
```

A derived class:

C#

```
public class StripeProcessor : PaymentProcessor
{
    public StripeProcessor() : base("Stripe")
    {
    }

    public override Task ProcessAsync(decimal amount)
    {
        Console.WriteLine($"Processing {amount}");
        return Task.CompletedTask;
    }
}
```

`StripeProcessor` inherits `LogStart()` and must implement `ProcessAsync()`.

Use an abstract class when related types share meaningful state or implementation and you want a common base.

### Interface

An interface defines a contract that a type can implement.

C#

```
public interface IPaymentProcessor
{
    Task ProcessAsync(decimal amount);
}
```

Different types can implement it:

C#

```
public class StripeProcessor : IPaymentProcessor
{
    public Task ProcessAsync(decimal amount)
    {
        return Task.CompletedTask;
    }
}

public class PayPalProcessor : IPaymentProcessor
{
    public Task ProcessAsync(decimal amount)
    {
        return Task.CompletedTask;
    }
}
```

A class can implement multiple interfaces:

C#

```
public class PaymentService :
    IPaymentProcessor,
    IDisposable,
    IAsyncDisposable
{
    // Implement required members
}
```

But a class can inherit from only one class (including an abstract class).

Interfaces can also contain default implementations and static members in modern C#, so the simplistic statement that an interface can only contain abstract method declarations is outdated. Their main role is still to define a contract independent of a shared class implementation.

### Comparison

|Feature|Abstract class|Interface|
| --- | --- | --- |
|Instance fields|Yes|No|
|Constructors|Yes|No instance constructors|
|Abstract members|Yes|Yes, through required contract members|
|Shared implementation|Yes|Yes, including default interface methods|
|Multiple inheritance|One base class|Multiple interfaces|
|Access modifiers|Broad member accessibility options|Contract members are generally public; newer features add more options|
|Typical use|Shared base behavior/state|Capability or contract|

A practical example:

An abstract `PaymentProcessor` could provide shared logging, configuration, and common processing steps. An `IPaymentProcessor` could simply describe the capability to process payments, allowing unrelated types to participate.

You can also use both:

C#

```
public abstract class PaymentProcessor : IPaymentProcessor
{
    public abstract Task ProcessAsync(decimal amount);
}
```

The abstract class provides a base implementation structure, while the interface allows code to depend on the contract.

## Putting the four OOP principles together

Imagine a notification system.

* Encapsulation: each sender protects its internal configuration and connection state.

* Inheritance: an `EmailSender` might derive from a shared notification base class if the relationship and shared behavior justify it.

* Polymorphism: the application can call `SendAsync()` through `INotificationSender` without knowing which sender it has.

* Abstraction: the interface hides provider-specific delivery details from the application.

The distinction to retain is that these principles are not four separate features you must use in every class. They are ways to reason about design.

In modern C# application development, you will often use encapsulation and abstraction constantly, polymorphism through interfaces frequently, and inheritance more selectively.

The important skill is choosing the simplest design that makes dependencies, state changes, and behavior clear.
