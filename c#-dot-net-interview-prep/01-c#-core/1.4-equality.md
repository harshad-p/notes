# 1.4 Equality

Equality in C# is about deciding when two values or objects should be considered the same.

This matters in everyday code, but especially when using collections such as `Dictionary<TKey, TValue>`, `HashSet<T>`, and LINQ operations like `Distinct()`.

Let’s separate the concepts first, then look at the different ways to implement or customize equality.

## 1. Reference equality vs. value equality

### Reference equality

Reference equality asks: Do these references point to the exact same object instance?

C#

```
var a = new Person { Name = "Harshad" };
var b = a;
var c = new Person { Name = "Harshad" };

Console.WriteLine(ReferenceEquals(a, b)); // true
Console.WriteLine(ReferenceEquals(a, c)); // false
```

* `a` and `b` refer to the same object.

* `c` is a different object, even though its data is identical.

For ordinary classes that don't customize equality, `Equals()` also uses reference equality by default.

### Value equality

Value equality asks: Do these objects represent the same logical value?

For example, two `Person` objects might be considered equal if their names match, regardless of whether they are separate instances.

C#

```
public class Person
{
    public string Name { get; set; } = "";

    public override bool Equals(object? obj)
    {
        return obj is Person other &&
               Name == other.Name;
    }
}
```

Now:

C#

```
var a = new Person { Name = "Harshad" };
var b = new Person { Name = "Harshad" };

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(ReferenceEquals(a, b)); // false
```

The objects are different instances, but they are equal according to the rule we defined.

Important: Value equality is a design decision. A person might instead be identified by a unique ID, so equal names wouldn't necessarily mean equal people.


## 2. `Equals()` and `GetHashCode()`

These two methods are closely related.

### `Equals()`

`Equals()` defines whether two objects are logically equal.

The base implementation on `object` uses reference equality. You can override it to define value equality.

A common pattern is to implement `IEquatable<T>` alongside the override:

C#

```
public class Person : IEquatable<Person>
{
    public int Id { get; set; }
    public string Name { get; set; } = "";

    public bool Equals(Person? other)
    {
        return other is not null && Id == other.Id;
    }

    public override bool Equals(object? obj)
    {
        return obj is Person other && Equals(other);
    }

    public override int GetHashCode()
    {
        return Id.GetHashCode();
    }
}
```

`IEquatable<Person>` provides a strongly typed equality method. It avoids needing to cast from `object` and is useful to generic collections and APIs that recognize it.

### `GetHashCode()`

A hash code is an integer used by hash-based collections to organize and find values efficiently.

The key contract is:

* If two objects are equal according to `Equals()`, they must return the same hash code.

* Two unequal objects may return the same hash code. This is called a collision.

* A hash code is not a unique identifier.

For example, a `HashSet<Person>` uses hash codes to narrow down where to look, then uses equality to determine whether an equal item is already present.

That means implementing `Equals()` without a compatible `GetHashCode()` can cause surprising behavior in dictionaries and hash sets.

Also: Don't mutate fields used for equality or hashing while an object is stored in a hash-based collection. The collection may have placed the object based on its old hash code and then fail to find it.

## 3. `==` operator

`==` is an operator, not simply another name for `Equals()`.

For most ordinary classes, `==` checks reference equality by default:

C#

```
var a = new Person { Id = 1, Name = "Harshad" };
var b = new Person { Id = 1, Name = "Harshad" };

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(a == b);      // false
```

Here, `Equals()` was overridden, but `==` was not.

You can overload `==` and `!=` to align them with your value-equality rules. If you do, implement them consistently and handle `null` correctly. Records generate these operators for you.

For strings, `==` compares string contents, not object identity:

C#

```
string a = new string("hello");
string b = new string("hello");

Console.WriteLine(a == b); // true
Console.WriteLine(ReferenceEquals(a, b)); // false
```

The behavior depends on the type's operator implementation.


## 4. Records and generated equality

Records are designed to support value-based equality with less boilerplate.

C#

```
public record Person(int Id, string Name);

var a = new Person(1, "Harshad");
var b = new Person(1, "Harshad");

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(a == b);      // true
```

For records, the compiler generates equality behavior based on the record's declared data members. It also generates `GetHashCode()`, `==`, and `!=`.

Records are useful when equality should mean that two instances contain equivalent data, such as configuration values, messages, or data-transfer objects.

One nuance: record equality is not automatically deep equality for every referenced object. For example, if a record contains a `List<string>`, that list is compared using its own equality behavior, which for `List<T>` is reference-based.

## 5. The different equality and comparison interfaces

There are a few similarly named interfaces in .NET. They solve different problems.

|Type|Purpose|Typical use|
| --- | --- | --- |
|`IEquatable<T>`|Defines equality for a type|`Person.Equals(Person?)`|
|`IEqualityComparer<T>`|Defines equality externally|Custom equality for a `HashSet<T>` or `Dictionary<TKey,TValue>`|
|`IComparer<T>`|Defines ordering between two values|Sorting by name, date, or priority|
|`IComparable<T>`|Defines a type's natural ordering|A type that can compare itself to another instance|

### `IEquatable<T>` — equality implemented by the type

This is what we used in the `Person` example:

C#

```
public class Person : IEquatable<Person>
{
    public int Id { get; set; }

    public bool Equals(Person? other)
    {
        return other is not null && Id == other.Id;
    }
}
```

Use it when equality is a natural, consistent part of the type's meaning.

For a complete implementation, remember to override `object.Equals()` and `GetHashCode()` too, as shown earlier.

### `IEqualityComparer<T>` — equality defined externally

Suppose `Person` equality is based on `Id`, but in one specific operation you want to treat people as equal when their names match.

You don't necessarily want to change the type's own equality rule. Instead, create a separate comparer:

C#

```
public class PersonNameComparer : IEqualityComparer<Person>
{
    public bool Equals(Person? x, Person? y)
    {
        return x?.Name == y?.Name;
    }

    public int GetHashCode(Person obj)
    {
        return obj.Name.GetHashCode();
    }
}
```

Use it with a collection:

C#

```
var people = new HashSet<Person>(new PersonNameComparer());

people.Add(new Person { Id = 1, Name = "Harshad" });
people.Add(new Person { Id = 2, Name = "Harshad" });

Console.WriteLine(people.Count); // 1
```

The set uses the supplied comparer instead of relying on `Person`'s default equality implementation.

This is particularly useful when:

* You need different equality rules in different contexts.

* You don't own the type.

* You want a case-insensitive comparison or a comparison based on selected fields.

For example, `StringComparer.OrdinalIgnoreCase` is a built-in comparer useful for case-insensitive string equality and hashing.

### `IComparer<T>` — ordering, not equality

`IComparer<T>` answers a different question: Which value should come first?

C#

```
public class PersonNameComparer : IComparer<Person>
{
    public int Compare(Person? x, Person? y)
    {
        return string.Compare(
            x?.Name,
            y?.Name,
            StringComparison.OrdinalIgnoreCase);
    }
}
```

Then:

C#

```
var people = new List<Person>
{
    new() { Id = 1, Name = "Zara" },
    new() { Id = 2, Name = "Alex" }
};

people.Sort(new PersonNameComparer());
```

The list is sorted by name, ignoring case.

`Compare(x, y)` conventionally returns:

* A negative number if `x` comes before `y`.

* Zero if they are equivalent in the ordering.

* A positive number if `x` comes after `y`.

Notice that returning zero does not necessarily mean `x.Equals(y)` is true. Two people with the same name but different IDs may compare as zero by name while remaining unequal by ID.

### `IComparable<T>` — the type defines its own ordering

Use `IComparable<T>` when a type has a natural ordering.

For example, a `Temperature` type might define that lower temperatures come before higher ones:

C#

```
public class Temperature : IComparable<Temperature>
{
    public double Celsius { get; init; }

    public int CompareTo(Temperature? other)
    {
        if (other is null)
            return 1;

        return Celsius.CompareTo(other.Celsius);
    }
}
```

Now `List<Temperature>.Sort()` can use that natural ordering without an external comparer.

`IComparer<T>` is useful when the ordering is external or there are multiple possible orderings. `IComparable<T>` is useful when the type itself has a sensible default order.


## 6. How the pieces fit together

### Equality and ordering decision guide

What are you trying to do?

Define what makes two instances of your type equal.

Use `IEquatable<T>` together with `Equals()` and `GetHashCode()`. Overload `==` and `!=` if operator equality should follow the same rule.

Use a different equality rule for a particular collection or operation.

Use `IEqualityComparer<T>`.

Give your type a natural sorting order.

Use `IComparable<T>`.

Sort using a particular criterion, or provide an alternative order.

Use `IComparer<T>`.

Your type is primarily a data value with value-based equality.

Consider a `record` or `record struct`.

## 7. Common interview pitfalls

* Overriding `Equals()` but not `GetHashCode()`: breaks the equality contract expected by hash-based collections.

* Assuming `==` and `Equals()` are identical: they can have different behavior.

* Confusing `IComparer<T>` with `IEqualityComparer<T>`: one defines ordering; the other defines equality and hashing.

* Assuming `Compare(x, y) == 0` means `x.Equals(y)`: not necessarily.

* Using mutable fields for equality: can cause lookup problems when objects are keys in a dictionary or members of a hash set.

* Assuming records always compare nested objects deeply: equality follows the equality behavior of each member's type.

The key distinction to remember:

* `Equals()` — are these considered equal?

* `GetHashCode()` — what hash bucket should this value use?

* `==` — what does equality syntax mean for this type?

* `IEquatable<T>` — how does this type define typed equality?

* `IEqualityComparer<T>` — how should equality be determined externally?

* `IComparable<T>` — how does this type order itself?

* `IComparer<T>` — how should two values be ordered externally?

## Follow-ups

> Does implementing IEquatable<Person> force you to implement any method? What does it enforce? It wasn't exactly clear from your explanation. 

Yes. Implementing `IEquatable<Person>` forces you to implement one method:

C#

```
bool Equals(Person? other);
```

That's the only method declared by the `IEquatable<T>` interface.

For example:

C#

```
public class Person : IEquatable<Person>
{
    public int Id { get; set; }
    public string Name { get; set; } = "";

    public bool Equals(Person? other)
    {
        return other is not null && Id == other.Id;
    }
}
```

If you declare `IEquatable<Person>` but don't implement `Equals(Person? other)`, the compiler reports an error unless the class is abstract.

### What does it actually enforce?

It enforces a strongly typed equality contract for your class.

Without `IEquatable<Person>`, you might only override the general-purpose method inherited from `object`:

C#

```
public override bool Equals(object? obj)
{
    return obj is Person other && Id == other.Id;
}
```

With `IEquatable<Person>`, you additionally provide a method that accepts a `Person` directly:

C#

```
public bool Equals(Person? other)
```

This has two main benefits:

* Type safety: the method accepts a `Person`, rather than an arbitrary `object`.

* Efficiency: it avoids unnecessary type checks and casts in code that can use the typed equality method.

Generic collections and other .NET APIs can use `IEquatable<T>` when available.

### Does it enforce the entire equality implementation?

No. This is an important distinction.

| Requirement                                  | Enforced by `IEquatable<Person>`? |
| -------------------------------------------- | --------------------------------- |
| Implement `Equals(Person? other)`            | Yes                               |
| Override `Equals(object? obj)`               | No                                |
| Override `GetHashCode()`                     | No                                |
| Overload `==` and `!=`                       | No                                |
| Ensure equality is symmetric and transitive  | No                                |
| Ensure equal objects have the same hash code | No                                |

The last two are logical requirements of a correct equality implementation, not compiler-enforced requirements.

For a typical class with value equality, you'd implement all the relevant pieces consistently:

C#

```
public class Person : IEquatable<Person>
{
    public int Id { get; set; }

    public bool Equals(Person? other)
    {
        return other is not null && Id == other.Id;
    }

    public override bool Equals(object? obj)
    {
        return obj is Person other && Equals(other);
    }

    public override int GetHashCode()
    {
        return Id.GetHashCode();
    }
}
```

Think of it this way: `IEquatable<Person>` requires you to provide the typed equality method. It doesn't automatically make your class's equality implementation complete or correct.

> What do you mean Ensure equality is symmetric and transitive?

These are two mathematical properties that a correct equality implementation should follow. They ensure that equality behaves consistently, regardless of the order in which objects are compared.

Let's use three `Person` objects to understand them.

### 1. Symmetry

If A equals B, then B must also equal A.

Mathematically:

A=B  ⟹  B=A

For example:

C#

```
var a = new Person { Id = 1 };
var b = new Person { Id = 1 };

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(b.Equals(a)); // true
```

Both comparisons return `true`.

Imagine an incorrect equality implementation that compares differently depending on the type of the other object:

C#

```
public class Person
{
    public int Id { get; set; }

    public override bool Equals(object? obj)
    {
        if (obj is Person other)
            return Id == other.Id;

        if (obj is Employee employee)
            return Id == employee.Id;

        return false;
    }
}

public class Employee : Person
{
}
```

This example alone doesn't necessarily violate symmetry because `Employee` inherits the implementation. But if `Employee` overrides `Equals()` to accept only other employees, a `Person` and an `Employee` with the same ID could produce different results depending on which object's `Equals()` is called.

That is the kind of inconsistency symmetry is meant to prevent.

### 2. Transitivity

If A equals B, and B equals C, then A must equal C.

Mathematically:

A=B ∧ B=C  ⟹  A=C

For example:

C#

```
var a = new Person { Id = 1 };
var b = new Person { Id = 1 };
var c = new Person { Id = 1 };

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(b.Equals(c)); // true
Console.WriteLine(a.Equals(c)); // true
```

All three objects have the same ID, so they are equal to one another.

An incorrect implementation might use a rule that isn't transitive. Consider equality based on whether two numbers differ by at most 1:

* `1` equals `2`.

* `2` equals `3`.

* But `1` does not equal `3`.

This violates transitivity.

For an equality implementation, you should avoid rules like this. Equality is meant to represent equivalence, not approximate similarity.

### 3. Other equality properties

There are two more useful properties to know:

| Property     | Meaning                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------- |
| Symmetry     | If `A.Equals(B)` is true, `B.Equals(A)` must also be true.                                  |
| Transitivity | If A equals B and B equals C, A must equal C.                                               |
| Reflexivity  | An object must equal itself: `A.Equals(A)` is `true`.                                       |
| Consistency  | Repeated comparisons should return the same result while the relevant state hasn't changed. |

`null` also has special handling: `Equals(null)` should return `false` for a non-null instance.

These properties are part of the expected equality contract, but the C# compiler doesn't check them for you.

Interview takeaway

When implementing `Equals()`, you're not just writing a condition that returns `true` or `false`. You're defining an equivalence relationship that should obey reflexivity, symmetry, transitivity, and consistency. This is important because collections and other code rely on equality behaving predictably.

> Does record implement Equals() method, and the == operator uses it?

Yes. A C# `record` automatically generates both `Equals()` and the `==` operator, and both use the record's generated value-equality rules.

For example:

C#

```
public record Person(int Id, string Name);

var a = new Person(1, "Harshad");
var b = new Person(1, "Harshad");

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(a == b);      // true
```

The compiler generates, among other members, behavior equivalent in concept to:

* `Equals(Person? other)` — compares the record's values.

* `Equals(object? obj)` — supports equality through the `object` API.

* `GetHashCode()` — generates a compatible hash code.

* `==` and `!=` — compare using the record's value-equality behavior.

One important nuance: `==` doesn't simply call the public `Equals(object?)` method. The compiler generates equality operators that use the record's equality logic, including its typed equality implementation.

You can think of it as:

C#

```
a == b
```

and

C#

```
a.Equals(b)
```

normally producing the same equality result for records.

However, they are still different mechanisms: one is an operator, and the other is a method. You can also customize equality behavior, so don't assume that every type in C# has this relationship.

Interview takeaway: Records generate value equality, including `Equals()`, `GetHashCode()`, and equality operators. Ordinary classes don't automatically get this behavior; you need to implement it yourself or use another suitable design.

> Just to clarify: == does a reference comparison, and by default, Equals() also does the same, but it can be overriden to perform value equality comparison? But then == operator can also be implemented to do the same. 

Yes, your understanding is correct. There is just one nuance worth keeping in mind.
For an ordinary C# class that hasn't customized equality:
- == performs reference equality by default.
- Equals() inherited from object also performs reference equality by default.
You can override Equals() to implement value equality. However, that does not automatically change the behavior of ==. You must overload the operator separately if you want it to use value equality too.
For example:
```
public class Person
{
    public int Id { get; set; }

    public override bool Equals(object? obj)
    {
        return obj is Person other && Id == other.Id;
    }

    public override int GetHashCode() => Id.GetHashCode();

    public static bool operator ==(Person? a, Person? b)
    {
        if (ReferenceEquals(a, b))
            return true;

        if (a is null || b is null)
            return false;

        return a.Equals(b);
    }

    public static bool operator !=(Person? a, Person? b) => !(a == b);
}
```
Now:
```
var a = new Person { Id = 1 };
var b = new Person { Id = 1 };

Console.WriteLine(a.Equals(b)); // true
Console.WriteLine(a == b);      // true
Console.WriteLine(ReferenceEquals(a, b)); // false
```
Notice that ReferenceEquals() still checks object identity, regardless of any custom equality implementation.

For a `record`, the compiler generates value equality and corresponding operators, so you generally don't need to write all of this yourself.
