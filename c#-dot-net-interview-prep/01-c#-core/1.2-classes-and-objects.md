# 1.2 Classes and Objects

This section is about how a class defines an object, and how C# controls **its state, visibility, and lifetime**.

---

## 1. Constructors

A constructor runs when an object is created.

```csharp
public class User
{
    public string Name { get; }

    public User(string name)
    {
        Name = name;
    }
}

var user = new User("Harshad");
```

`new User("Harshad")`:

1. Allocates the object.
2. Runs the constructor.
3. Returns a reference to the object.

The constructor is primarily responsible for establishing a **valid initial state**.

You can have multiple constructors:

```csharp
public class User
{
    public string Name { get; }
    public int Age { get; }

    public User()
    {
        Name = "Unknown";
    }

    public User(string name, int age)
    {
        Name = name;
        Age = age;
    }
}
```

You can also delegate one constructor to another:

```csharp
public User() : this("Unknown", 0)
{
}
```

This avoids duplicating initialization logic.

### Important interview point

A constructor is **not a method that you manually call later**. It is part of object creation and is invoked by the object creation process.

Also, constructors are **not inherited** by derived classes.

---

## 2. Fields

A field is storage belonging to an object or type.

```csharp
public class User
{
    private string name;
    private int age;
}
```

Each `User` object has its own `name` and `age`:

```text
User A → name = "Alice", age = 30
User B → name = "Bob",   age = 40
```

Unless the field is `static`.

```csharp
public class User
{
    public static int Count;
}
```

Now there is **one `Count` associated with the type**, not one per object.

```csharp
User.Count++;
```

---

## 3. Properties

A property provides controlled access to data.

```csharp
public class User
{
    public string Name { get; set; }
}
```

This looks like a field when you use it:

```csharp
user.Name = "Harshad";
Console.WriteLine(user.Name);
```

But conceptually, a property is an **access mechanism**, not simply a storage location.

You can control reading and writing:

```csharp
public string Name { get; private set; }
```

Outside the class:

```csharp
user.Name = "Bob"; // ❌
```

Inside the class:

```csharp
Name = "Bob";      // ✅
```

This is useful for maintaining invariants.

### Auto-properties

```csharp
public string Name { get; set; }
```

C# generates hidden backing storage for you.

You can also write it explicitly:

```csharp
private string _name;

public string Name
{
    get { return _name; }
    set { _name = value; }
}
```

The auto-property is essentially shorthand when you don't need custom getter/setter logic.

---

## 4. Fields vs Properties

This is an important distinction.

### Field

```csharp
private string _name;
```

It's directly storing state.

### Property

```csharp
public string Name { get; set; }
```

It's exposing an interface for accessing state.

Properties can contain logic:

```csharp
public string Name
{
    get => _name;
    set
    {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException();

        _name = value;
    }
}
```

You generally expose **properties** rather than public fields because properties give you control over how the state is accessed or changed.

---

## 5. Access modifiers

Access modifiers control **who can access a type/member**.

The main ones you'll use are:

```text
public
private
protected
internal
```

### `public`

Accessible from anywhere that can access the type.

```csharp
public string Name { get; set; }
```

### `private`

Accessible only inside the containing type.

```csharp
private string _name;
```

This is the default accessibility for class members if you don't specify one.

### `protected`

Accessible inside the class and derived classes.

```csharp
protected void Calculate()
{
}
```

### `internal`

Accessible within the same assembly.

This is particularly relevant when designing libraries.

```csharp
internal class Helper
{
}
```

There are also combinations such as:

```csharp
protected internal
private protected
```

You don't need to memorize these yet. The important idea is:

> **Access modifiers define the boundary of your API.**

For example:

```csharp
public class User
{
    private string _password;

    public string Name { get; set; }

    public bool CheckPassword(string password)
    {
        // Can access _password here
        ...
    }
}
```

Users of the class can interact with `Name` and `CheckPassword`, but don't directly manipulate `_password`.

That's encapsulation.

---

## 6. `static`

Normally, members belong to **an object instance**.

```csharp
var a = new User();
var b = new User();
```

Each object has its own instance state.

A `static` member belongs to the **type itself**.

```csharp
public class User
{
    public static int Count;
}
```

You access it through the type:

```csharp
User.Count++;
```

Not:

```csharp
a.Count++; // ❌ conceptually wrong
```

There is one `Count` shared by all `User` objects.

### Static methods

```csharp
public static int Add(int a, int b)
{
    return a + b;
}
```

Call:

```csharp
Math.Add(1, 2);
```

A static method doesn't have a particular object instance (`this`) to work with.

Therefore:

```csharp
public class User
{
    private string _name;

    public static void PrintName()
    {
        Console.WriteLine(_name); // ❌
    }
}
```

There is no particular `User` whose `_name` should be used.

---

## 7. `readonly`

`readonly` means:

> **This field can only be assigned during initialization or construction.**

```csharp
public class User
{
    private readonly int _id;

    public User(int id)
    {
        _id = id;
    }
}
```

After construction:

```csharp
_id = 10; // ❌
```

You can also initialize it directly:

```csharp
private readonly int _id = 10;
```

The important distinction is that `readonly` applies to **fields**, not properties.

You can have:

```csharp
public int Id { get; }
```

which gives you an effectively read-only property from outside.

But technically, that's a property with no setter, whereas:

```csharp
private readonly int _id;
```

is a readonly field.

### `readonly` does not mean deeply immutable

This is an important interview trap.

```csharp
private readonly List<string> _names = new();
```

You cannot replace the list:

```csharp
_names = new List<string>(); // ❌
```

But you **can modify the list itself**:

```csharp
_names.Add("Harshad"); // ✅
```

Why?

Because `readonly` prevents changing the **reference stored in the field**, not the object that the reference points to.

---

## 8. `const`

`const` means the value is a **compile-time constant**.

```csharp
public const int MaxRetries = 3;
```

You cannot change it:

```csharp
MaxRetries = 5; // ❌
```

And the value must be something the compiler can evaluate at compile time.

For example:

```csharp
const int Max = 10;
const string Name = "Harshad";
const double Pi = 3.14;
```

But:

```csharp
const DateTime Now = DateTime.Now; // ❌
```

because `DateTime.Now` is evaluated at runtime.

---

### `const` vs `readonly`

This distinction is very important.

```csharp
const int A = 10;

readonly int B;

public MyClass(int value)
{
    B = value;
}
```

#### `const`

- compile-time constant
- value must be known at compile time
- implicitly `static`
- cannot be changed

#### `readonly`

- runtime value
- can be assigned during construction
- each object can have a different value
- cannot be reassigned after construction

For example:

```csharp
public class User
{
    public const string Company = "Atain";

    public readonly int Id;

    public User(int id)
    {
        Id = id;
    }
}
```

Every `User` has its own `Id`:

```text
User 1 → Id = 100
User 2 → Id = 200
```

But `Company` is one compile-time constant.

---

## 9. `init`

`init` gives you a property that can be assigned **during object initialization**, but not normally changed afterward.

```csharp
public class User
{
    public string Name { get; init; }
    public int Age { get; init; }
}
```

You can do:

```csharp
var user = new User
{
    Name = "Harshad",
    Age = 37
};
```

But afterward:

```csharp
user.Name = "Bob"; // ❌
```

This is different from:

```csharp
public string Name { get; set; }
```

where you can change it anytime.

### Why is `init` useful?

It lets you create an immutable-style object without requiring a constructor with many parameters.

Compare:

```csharp
var user = new User("Harshad", 37, "Germany");
```

with:

```csharp
var user = new User
{
    Name = "Harshad",
    Age = 37,
    Country = "Germany"
};
```

while still preventing later mutation.

---

## Putting them together

Consider:

```csharp
public class User
{
    public const int MaxAge = 120;

    private readonly int _id;

    public string Name { get; init; }

    public int Age { get; set; }

    public static int UserCount { get; private set; }

    public User(int id, string name)
    {
        _id = id;
        Name = name;
        UserCount++;
    }
}
```

Each concept has a different purpose:

| Feature | What it controls |
|---|---|
| Constructor | Initial object creation/state |
| Field | Stores state |
| Property | Exposes controlled access to state |
| Access modifier | Who can access something |
| `static` | Belongs to the type rather than an instance |
| `readonly` | Field can't be reassigned after initialization |
| `const` | Compile-time constant |
| `init` | Property can be assigned during initialization only |

The big mental model I'd keep is:

> **Fields store state. Properties expose state. Constructors establish initial state. Access modifiers control the boundary. `static` changes ownership from object → type. `readonly`/`init` restrict mutation, while `const` represents a compile-time constant.**

## Follow-ups

> When you were explaining Properties, you said: This is useful for maintaining invariants. Please elaborate.

An **invariant** is a condition that should **always be true about an object while that object is in a valid state**.

Properties are useful for maintaining invariants because they let you **control how state can be changed**, rather than allowing callers to freely modify fields.

### Simple example

Suppose we have a bank account.

One invariant could be:

> The account balance must never be negative.

If we expose the balance as a public field:

```csharp
public class BankAccount
{
    public decimal Balance;
}
```

Anyone can do:

```csharp
account.Balance = -500;
```

Now the object is in an invalid state. We've violated the invariant.

### A property lets us control the change

```csharp
public class BankAccount
{
    private decimal _balance;

    public decimal Balance
    {
        get => _balance;
        private set
        {
            if (value < 0)
                throw new ArgumentException("Balance cannot be negative.");

            _balance = value;
        }
    }
}
```

Now external code cannot directly change the balance:

```csharp
account.Balance = -500; // ❌
```

Instead, we expose operations that enforce the rules:

```csharp
public void Deposit(decimal amount)
{
    if (amount <= 0)
        throw new ArgumentException();

    Balance += amount;
}

public void Withdraw(decimal amount)
{
    if (amount <= 0)
        throw new ArgumentException();

    if (amount > Balance)
        throw new InvalidOperationException();

    Balance -= amount;
}
```

Now the class itself controls all transitions between states.

### The important idea

Think of an object as having a set of **valid states**:

```text
             BankAccount
                  │
        ┌─────────┴─────────┐
        │                   │
   Valid state          Invalid state
   Balance >= 0         Balance < 0
```

The object's methods/properties become the **gatekeepers** that prevent it from entering an invalid state.

That's what we mean by maintaining an invariant.

### Another example: order status

Imagine:

```csharp
public class Order
{
    public string Status { get; set; }
}
```

Someone can now do:

```csharp
order.Status = "Banana";
```

Or:

```csharp
order.Status = "Shipped";
order.Status = "Pending";
```

Maybe your business rules say:

```text
Pending → Paid → Shipped → Delivered
```

and a shipped order cannot go back to pending.

Those rules are invariants/business rules that should be protected by the object's API.

You might instead have:

```csharp
public class Order
{
    public OrderStatus Status { get; private set; }

    public void MarkAsPaid()
    {
        if (Status != OrderStatus.Pending)
            throw new InvalidOperationException();

        Status = OrderStatus.Paid;
    }

    public void Ship()
    {
        if (Status != OrderStatus.Paid)
            throw new InvalidOperationException();

        Status = OrderStatus.Shipped;
    }
}
```

Now callers can't arbitrarily manipulate the state.

### Why this is related to encapsulation

This is really the deeper reason we talked about **properties instead of public fields**.

Bad encapsulation:

```csharp
public class BankAccount
{
    public decimal Balance;
}
```

The outside world can manipulate the object's internal state however it wants.

Better encapsulation:

```csharp
public class BankAccount
{
    private decimal _balance;

    public decimal Balance => _balance;

    public void Deposit(decimal amount) { ... }
    public void Withdraw(decimal amount) { ... }
}
```

The outside world can **observe** the balance but cannot arbitrarily change it.

So:

> **An invariant is a rule that must remain true for a valid object. Encapsulation gives the object control over how its state changes, allowing it to protect those rules.**

This is one of the reasons `private set`, `init`, validation in setters, and methods such as `Deposit()`/`Withdraw()` are useful.

> So basically, `public int Balance { get; set; }` is the same as `public int _balance`? If there are no restrictions on the property, we can basically use the field it seems. 

`public int Balance { get; set; }` is **not exactly the same** as `public int _balance`.

### What they have in common

If you write:

```csharp
public int Balance { get; set; }
```

C# creates **hidden backing storage** for that property.

Conceptually, it's roughly like:

```csharp
private int _balance;

public int Balance
{
    get => _balance;
    set => _balance = value;
}
```

So in this specific case, you're right: **there's no validation, restriction, or custom behavior, so the property is essentially exposing a piece of storage with automatic get/set access.**

### But why not just make the field public?

You could:

```csharp
public int Balance;
```

But a property gives you an **abstraction boundary**.

Today:

```csharp
public int Balance { get; set; }
```

Later, you can change it to:

```csharp
public int Balance
{
    get => _balance;
    set
    {
        if (value < 0)
            throw new ArgumentException();

        _balance = value;
    }
}
```

And callers still use:

```csharp
account.Balance = 100;
```

The calling code doesn't change.

That's one of the major reasons properties are preferred for an object's public API.

### There's another important difference

Properties can also have **different accessibility for reading and writing**:

```csharp
public int Balance { get; private set; }
```

Now:

```csharp
Console.WriteLine(account.Balance); // ✅
account.Balance = 100;              // ❌
```

You couldn't express that with a simple public field.

You could make the field private:

```csharp
private int _balance;
```

but then outside code can't read it either.

### So your intuition is correct with one refinement

If you have:

```csharp
public int Balance { get; set; }
```

and there is genuinely **no need for encapsulation, validation, different access levels, or future behavior**, then the property's behavior is essentially just:

```text
store a value
   ↑    ↓
 get  set
```

But for **public APIs**, properties are generally preferred because they give you that abstraction boundary.

That's why you'll very commonly see:

```csharp
public string Name { get; set; }
```

rather than:

```csharp
public string Name;
```

Even when the property currently does nothing more than store and retrieve a value.

> Can you explain the different scenarios for all the access modifiers applied to fields, properties, methods, classes, etc. including readonly, static, sealed, public, private, protected, internal, etc.? Maybe some cannot be applied to some.

Yes. This is actually a good point to build a **mental model of C# modifiers**, because several of them can be combined, while others apply only to particular kinds of members.

I'll separate **accessibility modifiers** (`public`, `private`, etc.) from **behavior/modifier keywords** (`static`, `readonly`, `sealed`, etc.).

### 1. First: two different categories

#### Accessibility modifiers

These answer:

> **Who is allowed to access this thing?**

- `public`
- `private`
- `protected`
- `internal`
- `protected internal`
- `private protected`

#### Other modifiers

These answer things like:

> **How does this thing behave?**

- `static`
- `readonly`
- `const`
- `sealed`
- `abstract`
- `virtual`
- `override`
- `new`
- `required`
- `init` — technically an accessor keyword rather than a general modifier

These categories can often be combined.

For example:

```csharp
public static readonly int MaxRetries = 3;
```

`public` → who can access it  
`static` → belongs to the type  
`readonly` → field can't be reassigned after initialization

---

### 2. Accessibility modifiers

#### `public`

Accessible from anywhere that can access the containing type.

```csharp
public class User
{
    public string Name { get; set; }

    public void Login()
    {
    }
}
```

Use it when something is deliberately part of the **public API**.

Typical examples:

```csharp
public class UserService
public User GetUser()
public string Name { get; }
```

---

#### `private`

Accessible only within the containing type.

```csharp
public class User
{
    private string _password;

    private void ValidatePassword()
    {
    }
}
```

Use it for **implementation details** that callers shouldn't directly manipulate.

This is the default accessibility for class members if you don't specify one.

```csharp
class User
{
    string _name; // private
}
```

---

#### `protected`

Accessible from:

1. the containing class
2. derived classes

```csharp
public class Animal
{
    protected void Move()
    {
    }
}

public class Dog : Animal
{
    public void Run()
    {
        Move(); // ✅
    }
}
```

But:

```csharp
var dog = new Dog();
dog.Move(); // ❌
```

So `protected` essentially says:

> "This is part of the inheritance interface, but not the public interface."

Be careful with it: extensive use of protected members can create tight coupling between base and derived classes.

---

#### `internal`

Accessible anywhere within the **same assembly**.

```csharp
internal class PaymentProcessor
{
}
```

This is very useful in libraries.

Imagine:

```text
MyCompany.Payments.dll
│
├── public PaymentService
├── public Payment
└── internal PaymentProcessor
```

Consumers of your DLL see the public API but cannot access `PaymentProcessor`.

Code inside the same assembly can.

---

#### `protected internal`

This one is confusing.

It means:

> Accessible from the same assembly **OR** from a derived class.

So:

```csharp
protected internal void DoSomething()
```

allows either:

```text
Same assembly
     OR
Derived class
```

It does **not** mean "protected AND internal."

---

#### `private protected`

This is the opposite combination:

> Accessible from the same assembly **AND** from a derived class.

So:

```csharp
private protected void DoSomething()
```

means the member is available to derived classes, but only if that derived class is in the same assembly.

A useful way to remember:

```text
protected internal = OR
private protected   = AND
```

---

### 3. Where can accessibility modifiers be used?

Roughly:

| Construct | public | private | protected | internal |
|---|---:|---:|---:|---:|
| Class | ✅ | ✅ nested only | ❌ top-level | ✅ |
| Struct | ✅ | ✅ nested only | ❌ | ✅ |
| Field | ✅ | ✅ | ✅ | ✅ |
| Property | ✅ | ✅ | ✅ | ✅ |
| Method | ✅ | ✅ | ✅ | ✅ |
| Constructor | ✅ | ✅ | ✅ | ✅ |
| Nested class | ✅ | ✅ | ✅ | ✅ |

One important exception:

#### Top-level classes

A top-level class cannot be `private` or `protected`.

```csharp
private class User // ❌
```

because there is no containing type relative to which "private" or "protected" would make sense.

It can be:

```csharp
public class User
```

or:

```csharp
internal class User
```

If you nest it:

```csharp
public class Outer
{
    private class Inner
    {
    }
}
```

then `private` makes sense.

### 4. `static`

`static` changes **ownership**.

Without `static`:

```csharp
public class User
{
    public string Name { get; set; }
}
```

Each object has its own `Name`.

```text
User A → Name = Alice
User B → Name = Bob
```

With `static`:

```csharp
public class User
{
    public static int Count;
}
```

there is one `Count` for the type:

```text
User
 └── Count = 10
```

You access it through the type:

```csharp
User.Count
```

#### Static can apply to:

- fields
- properties
- methods
- constructors → special `static` constructor
- classes
- events
- operators

But a `static` member cannot use instance state directly:

```csharp
class User
{
    private string _name;

    public static void Print()
    {
        Console.WriteLine(_name); // ❌
    }
}
```

There is no particular `User` instance.

---

### 5. `readonly`

`readonly` is primarily a **field modifier**.

```csharp
private readonly int _id;
```

It means:

> The field can be assigned during initialization/construction, but cannot later be reassigned.

```csharp
public User(int id)
{
    _id = id; // ✅
}

public void Change()
{
    _id = 20; // ❌
}
```

#### Important

`readonly` does **not** mean the referenced object is immutable.

```csharp
private readonly List<string> _names = new();
```

This is illegal:

```csharp
_names = new List<string>(); // ❌
```

but this is fine:

```csharp
_names.Add("Harshad"); // ✅
```

because the reference hasn't changed.

---

### 6. `const`

`const` is an even stronger concept.

```csharp
public const int MaxRetries = 3;
```

It means:

> This value is a compile-time constant.

A `const` member is implicitly `static`.

So:

```csharp
User.MaxRetries
```

not an instance-specific value.

You can't have:

```csharp
public const int MaxRetries;

public User(int retries)
{
    MaxRetries = retries; // ❌
}
```

because the compiler must know the value at compile time.

#### `const` vs `readonly`

```csharp
public const int A = 10;

public readonly int B;

public MyClass(int value)
{
    B = value;
}
```

Think:

```text
const
  ↓
known by compiler
  ↓
same fixed value

readonly
  ↓
known at runtime
  ↓
can be different per object
```

---

### 7. `sealed`

`sealed` means:

> **Don't allow further inheritance/overriding.**

It has two important uses.

#### Sealed class

```csharp
public sealed class PaymentProcessor
{
}
```

Now:

```csharp
class MyProcessor : PaymentProcessor // ❌
{
}
```

Why would you do this?

Sometimes a type isn't designed to be inherited from, or you explicitly want to prevent extension through inheritance.

---

#### Sealed override

You can also seal an overridden member:

```csharp
public class Animal
{
    public virtual void Move()
    {
    }
}

public class Dog : Animal
{
    public sealed override void Move()
    {
    }
}
```

Now a class derived from `Dog` cannot override `Move()` again.

```csharp
public class Labrador : Dog
{
    public override void Move() // ❌
    {
    }
}
```

So:

```text
sealed class
    → no one can inherit from the class

sealed override
    → descendants can't override this member anymore
```

---

### 8. `virtual`

`virtual` means:

> Derived classes are allowed to replace this implementation.

```csharp
public class Animal
{
    public virtual void Speak()
    {
        Console.WriteLine("Animal sound");
    }
}
```

Derived class:

```csharp
public class Dog : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Woof");
    }
}
```

This enables runtime polymorphism.

---

### 9. `override`

`override` means:

> I'm providing a new implementation for an inherited `virtual`/`abstract` member.

```csharp
public class Dog : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Woof");
    }
}
```

The base member must generally be:

```text
virtual
abstract
override
```

for you to override it.

---

### 10. `abstract`

`abstract` means:

> This is intentionally incomplete and must be implemented by a derived type.

Example:

```csharp
public abstract class Animal
{
    public abstract void Speak();
}
```

You can't do:

```csharp
var animal = new Animal(); // ❌
```

A derived class must implement it:

```csharp
public class Dog : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Woof");
    }
}
```

An abstract method has no implementation:

```csharp
public abstract void Speak();
```

An abstract class can also contain normal implementation:

```csharp
public abstract class Animal
{
    public string Name { get; set; }

    public void Eat()
    {
        // implementation
    }

    public abstract void Speak();
}
```

---

### 11. `new`

This one is different.

`new` on an inherited member means:

> I'm intentionally hiding the inherited member rather than overriding it.

```csharp
public class Animal
{
    public void Speak()
    {
        Console.WriteLine("Animal");
    }
}

public class Dog : Animal
{
    public new void Speak()
    {
        Console.WriteLine("Dog");
    }
}
```

This is **not polymorphic overriding**.

That's an important distinction:

```text
override
    → replace inherited virtual behavior

new
    → hide inherited member
```

---

### 12. `init`

`init` applies to a **property accessor**.

```csharp
public string Name { get; init; }
```

It means:

> You can set this property during object initialization, but not afterward.

```csharp
var user = new User
{
    Name = "Harshad"
};

user.Name = "Bob"; // ❌
```

It is useful for immutable-style objects.

---

### 13. `get` / `set` aren't modifiers

They're property accessors:

```csharp
public int Age
{
    get;
    set;
}
```

You can control their accessibility:

```csharp
public int Age { get; private set; }
```

This is extremely common.

It means:

```text
outside class → can get
inside class  → can get + set
```

You can also do:

```csharp
public int Age { private get; set; }
```

though this is less common.

---

### 14. Putting modifiers together

Now you can start seeing why combinations exist.

### Shared constant

```csharp
public const int MaxRetries = 3;
```

`public` → externally visible  
`const` → compile-time constant  
`const` is implicitly static

---

#### Per-object immutable field

```csharp
private readonly int _id;
```

`private` → implementation detail  
`readonly` → cannot reassign after construction  
not static → each object gets its own value

---

#### Shared mutable state

```csharp
private static int _count;
```

`private` → only class can access it  
`static` → one value shared by all instances

---

#### Public read-only property

```csharp
public string Name { get; }
```

Anyone can read it, but nobody can normally assign it after construction.

---

#### Public property with internally controlled mutation

```csharp
public decimal Balance { get; private set; }
```

External code can observe it, but only the class can change it.

---

#### Extensible base class

```csharp
public abstract class PaymentProcessor
{
    public abstract void Process();
}
```

`public` → publicly accessible type  
`abstract` → can't instantiate directly  
abstract method → derived implementations required

---

#### Prevent further inheritance

```csharp
public sealed class StripePaymentProcessor
{
}
```

Public type, but inheritance is explicitly prohibited.

---

### The mental model

Don't try to memorize these as one giant list. Think in dimensions:

```text
                    C# member/type
                          │
        ┌─────────────────┼──────────────────┐
        │                 │                  │
   WHO CAN SEE IT?   HOW IS IT OWNED?   CAN IT CHANGE?
        │                 │                  │
 public/private       static/instance    readonly/const
 protected/internal
        │
        │
   INHERITANCE?
        │
 virtual/override
 abstract/sealed
 new
```

And properties have their own mutation controls:

```text
Property
   │
   ├── get
   ├── set
   └── init
```

That mental model is much more useful than memorizing which keyword goes beside which declaration.

One particularly important distinction to keep in mind for interviews is:

**`private`, `protected`, `internal`, and `public` control accessibility. They don't make something immutable.**

**`readonly`, `const`, and `init` restrict mutation/assignment.**

**`static` changes whether something belongs to an instance or the type.**

**`virtual`, `override`, `abstract`, `sealed`, and `new` control inheritance/polymorphism.**
